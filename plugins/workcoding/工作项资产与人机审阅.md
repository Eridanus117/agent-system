# 工作项资产与人机审阅

> 状态：试行裁定。该文件记录 WorkCoding 的资产模型，不是某个业务 Change 的实施方案。

## 结论

WorkCoding 不以 OpenSpec 作为顶层研发工作流。

WorkCoding 的基本单位是**工作项**，不是 `Change`。一个工作项可以是：

- 改既有代码；
- 查一个问题或一组数据；
- 设计一项能力；
- 做一次集成、发布或回滚；
- 整理一段遗留系统；
- 修改规则或文档。

OpenSpec 可以作为某类工作的输入、交付投影或历史资产，但不规定所有工作的目录、阶段和生命周期。

## 为什么不以 OpenSpec 为顶层

OpenSpec 更适合表达：

```text
一个 Change → 一组规格 → 实施 → 验收 → 归档
```

WorkCoding 要解决的是：

```text
一个工作项 → 多次人-Agent 协作 → 关键判断审阅 → 执行 → 证据 → 冷启动续接
```

两者的中心不同：

| OpenSpec | WorkCoding |
|---|---|
| 规格和 Change | 工作项和决策 |
| 阶段推进 | 人-Agent 交互 |
| 文档交付 | 判断审阅和纠偏 |
| 验收结果 | 当前状态、下一步和证据 |
| 归档生命周期 | 跨 Session 冷启动 |

OpenSpec 资产不删除、不强行迁移；现有 OpenSpec 内容按历史资产或项目证据保留。新工作不再默认套入 OpenSpec。

## 工作项资产模型

每个工作项一份资产集合，目录和文件名优先使用中文。固定导航文件仍使用 `index.md`，因为它是工具和知识库的约定入口。

建议形态：

```text
工作项/
└── <工作项>/
    ├── index.md
    ├── 当前状态.md
    ├── 目标与边界.md
    ├── 当前事实.md
    ├── 方案与决策.md
    ├── 审阅记录.md
    ├── 执行计划.md
    ├── 验证证据.md
    └── 执行资产/
```

### 各资产只回答一个问题

| 资产 | 问题 |
|---|---|
| `index.md` | 这个工作项有什么，应该先读什么 |
| `当前状态.md` | 现在到哪里，下一步是什么 |
| `目标与边界.md` | 要解决什么，不解决什么 |
| `当前事实.md` | 代码、环境、数据当前确实是什么 |
| `方案与决策.md` | 采用什么方案，为什么排除其他方案 |
| `审阅记录.md` | 人确认或否决了哪些判断 |
| `执行计划.md` | Agent 按什么顺序执行，每步如何停和退 |
| `验证证据.md` | 如何证明改对、老逻辑没坏、发布可控 |
| `执行资产/` | 可运行脚本、fixture、回放输入和机器结果在哪里 |

`index.md` 是导航和当前摘要，不重复详细正文；正文是当前认识；审阅记录保留纠偏历史；执行资产和证据不能反过来替代人的产品或方案裁定。

## 人-Agent 审阅协议

人不审阅 Agent 的全部思考，也不只在最后审阅代码 diff。Agent 必须在高代价动作前提交短审阅卡，人只审当前判断。

审阅卡统一包含：

```text
对象｜正在审什么
判断｜Agent 当前认为是什么
证据｜依据哪段代码、哪条输入或哪个结果
假设｜哪些内容还没有证据
风险｜判断错了会造成什么
请求｜请确认 / 否决第 N 条 / 要求补证
结果｜待审 / 已确认 / 已否决 / 已纠偏
```

### 固定人审点

- 路线：这是什么形状，走哪些规程，跳过什么以及为什么；
- 需求：需求句和真实例子是否准确；
- 现状：真实输入实际走了哪条老路径；
- 改法：新逻辑放在哪里，旧路径是否保持；
- 集成：谁调谁、哪些边界变了、每步能否单独退出；
- 发布：放量条件、观测信号和回滚点；
- 证据：样本覆盖是否足够，老路径是否与改前母版一致。

未经人明确确认，Agent 不得把当前草案当作授权，不得跨过对应的高风险动作。

### 审阅结果

统一使用以下结果之一：

```text
待审
已确认
已否决
已纠偏
待补证
```

人否决后不覆盖旧判断，记录：

```text
原判断｜...
人纠偏｜...
新判断｜...
```

沉默不等于确认；Agent 不得用“没有反对”推进。

## 冷启动要求

工作项必须允许人在五天后只读少量入口，重新回答：

1. 这是什么工作？
2. 为什么这样做？
3. 现在做到哪里？
4. 哪些已经确认？
5. 哪些仍未决定？
6. 下一步是什么？
7. 证据在哪里？

冷启动入口优先读取：

```text
index.md
当前状态.md
审阅记录.md 的最近有效裁定
验证证据.md 的当前结果
```

每次 Session 结束前，至少维护：

- 当前状态；
- 最近有效裁定；
- 未决事项；
- 下一步动作；
- 新增证据入口。

不把“今天做了什么、然后发现什么”当作当前状态。时间线可以留在日志或纠偏记录里，不能成为冷启动的唯一入口。

## 资产真源与分层

```text
WorkCoding 插件
    → 定义通用规程和审阅协议

工作项资产
    → 保存当前工作项的事实、判断、执行和证据

项目代码与运行态
    → 当前行为和实际结果的最高证据

知识库
    → 多次工作验证后的可迁移方法
```

项目局部的模板 ID、分支、环境、接口调用和执行结果留在工作项或项目仓；只有可迁移的方法论进入知识库。

## 资产归属边界

`agent-system` 只保存 WorkCoding 的通用方法和执行能力，不保存任何具体工作的业务内容。

允许进入 `agent-system`：

- 通用规程和路由规则；
- 审阅卡的结构和状态协议；
- 中文资产模板；
- 通用检查器、执行器和不带真实业务数据的示例；
- 已从多个工作项蒸馏出的通用方法。

禁止进入 `agent-system`：

- 某个工作的需求原话、产品决定和业务范围；
- 项目代码路径、分支、提交、环境和部署事实；
- 真实账号、模板 ID、订单 ID、日志内容和接口出入参；
- 某个工作项的审阅记录、当前状态、执行计划和验证证据；
- 还未经负责人确认的业务假设。

具体工作内容必须进入它所属的工作资产仓、项目仓或受权限边界保护的工作项目录。WorkCoding 插件只读取或生成这些资产，不拥有它们。

`工作项资产与人机审阅.md` 本身属于方法设计记录，不属于任何具体工作的内容。

同一事实可以有不同视图，但只能有一个事实源：

- Markdown 适合人审和冷启动；
- JSON/YAML/fixture 适合执行器；
- runner 和命令输出提供验证证据；
- 任何投影都不能伪造未确认的裁定。

## 案例与方法边界

WorkCoding 方法文件不定义具体业务域的完整需求，也不把某个业务案例当作工作流模型的依据。

具体业务案例的名称、范围和能力清单属于案例资产，不写入通用 WorkCoding 方法结论。

通用方法只规定：

- 工作项如何建立；
- 当前状态如何维护；
- 人-Agent 在哪些判断点交互；
- 审阅、确认、否决和纠偏如何留痕；
- 执行资产和验证证据如何关联；
- 新 Session 如何冷启动。

具体业务工作项应在自己的资产目录中定义目标、切片、边界和证据，不能反过来改变通用方法的基本单位。

## 当前试行边界

- 本模型先用一个现有业务工作项验证，不把该案例需求混入通用方法；
- 案例资产由所属工作资产仓维护，不由 WorkCoding 插件保存业务事实；
- 首先验证冷启动和人审是否有效，再决定是否建立更多固定文件；
- 不因目录设计而批量重写已有插件或历史资产；
- 不把 WorkCoding 设计文档当成业务需求授权，具体工作项仍须由负责人确认范围和裁定。
