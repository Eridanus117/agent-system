# 需求洞察：先翻回问题，再让主人去问

工作里的需求从产品来，第一句永远是「解」——「要支持 X」。X 已经预设了问题是什么、这是最好的解法、值得做。本 skill 做的事：**把 X 翻回问题，备好问题让主人去问提出方，收口成三行加一句「解到什么样算解了」。** 这是 ISO 12207 的 6.4.1 业务或使命分析在 workCoding 里的规程。

真源在个人知识库 `notes/需求洞察.md`（与标准的对照、备选与不选理由、裁决史、未解决）；步骤在本文。

## 为什么需要它

`clarify` 问的是主人自己；这里痒点来自提出方，agent 问不到，主人是中间人。所以 agent 的动作从「问」变成**备问题、收答案、下断言**，问的动作主人去做。另外 6.4.1 要求一条产出 clarify 没有：初步确认判据——「解到什么样算解了」，它直接喂后面 `requirement-translation` 的例子和自测验收，三条规程共用同一条判据。

根本认识（`notes/需求分析.md`）：需求方的陈述是待分析的输入，不是证据。

## 三条铁律

1. **原话一字不改，加谁提的。**
   理由：原话是唯一的证据；改一个字，后面所有断言都失去对照物。
2. **对主人给断言，对提出方给历史行为问题。**
   对主人写「提出方真正的问题是 P，不是 X」，不写「你觉得他们要什么」；给提出方的三个问题只问过去发生过的事（上次怎么办的、现在怎么忍的、不做会怎样），不问「你想要什么功能」。
   理由：主人对「这句不对」的判断比对开放题快十倍；提出方的意见会现编，历史能回忆。
3. **主人否过之前不落盘；拿不出证据的一句写「假设」。**
   查现成查不到时写「未查到」，不写「没有」。
   理由：草案是拿来被否的，先落盘等于默认它对。

纠偏留痕：主人或提出方否了草案，记「原写 A，裁为 B」在草案下面，不覆盖。

## 五个工位

判形状与摆路线不在这里——那是 `workcoding` 路由的事，进到本 skill 时路线已经确认过。

| 工位 | 干什么 | 槽位里的实践 |
|---|---|---|
| **1 抄原话，判解还是问题** | 原话一字不改加谁提的。判它是「解」还是「问题」；是解就写断言草案：「提出方真正的问题是 P，不是 X」 | clarify 工位 1，把解翻回问题 |
| **2 备三个问题** | 按草案生成三个问历史行为的问题：上次遇到怎么办的、现在怎么忍的、不做会怎样。主人拿去问提出方，把原话带回 | JTBD 切换访谈；29148 需求获取 |
| **3 查现成** | 现有模板、配置、运营手段能不能覆盖；查工作语境笔记「系统地图」与「领域术语」。雇主语境的 buy 即「用现有能力」。查不到写「未查到」 | clarify 工位 3；buy vs build |
| **4 收口三行加一句** | 真正的问题 / 值不值得改（含不改的路）/ 往哪个方向改；第四句「解到什么样算解了」，一条可观察判据 | clarify 收口；12207 6.4.1 初步确认判据 |
| **5 留** | 主人带回答案、否过三行之后：原话、三个问答、三行加一句进工作语境笔记「干系人与需求实例」，同时是改动记录「拆」一节的开头；`requirement-translation` 从这里开始 | 工作语境笔记；改动记录 |

工位 1–4 一次出完给主人，工位 5 等主人回来。Pre-mortem 泼冷水只在大改动时加，小改动跳过（备选与不选理由见真源笔记）。

## 产出：一段草案，没有别的

```
原话｜<一字不改>（提：<谁>）
判｜这是解。草案：提出方真正的问题是 <P>，不是 <X>
问提出方｜1 上次遇到这种情况你们怎么办的？ 2 现在怎么忍过来的？ 3 不做会怎样？
查现成｜<现有能力能不能覆盖 / 未查到>
三行｜问题是 <…> ｜ <值得改 / 不值得 / 先不改>—— <理由> ｜ 方向是 <…>，排除 <…> 因 <…>
判据｜解到什么样算解了：<一条可观察判据>
请把三个问题的原话带回来；三行和判据哪句不对直接否。
```

例子：

```
原话｜运费模板要支持按省份设偏远附加（提：产品 A）
判｜这是解。草案：真正的问题是新疆西藏的实际运费高于统一附加，商家在亏钱
问提出方｜上次怎么办的 → ？ ｜ 现在怎么忍 → ？ ｜ 不做 → ？
查现成｜模板有「区域加价」字段但只到大区，不到省
三行｜问题是偏远省份运费缺口由人工补 ｜ 值得改（假设：等提出方带回频率与代价）｜ 方向是省级附加表，排除大区字段细化因它被别的模块共用
判据｜新疆单不再进补贴导表，连续两周
```

**主人带答案回来、否过三行之前：不写文件、不翻 EARS 句、不进任何后续规程。**

## 路由边界

| 相邻 | 它管什么 | 分界（可测） |
|---|---|---|
| **`clarify`** | 主人自己冒出的「我想建个 X」痒点 | **来源**：痒点来自主人自己 → clarify；需求来自提出方 → 本 skill |
| **`workcoding`** | 判形状、摆路线、等确认 | **时机**：路线确认之前是它；本 skill 不判形状、不摆路线 |
| **`requirement-translation`** | 把收口后的需求翻成 EARS 句加例子 | **状态**：三行加一句已被主人否过 → 翻译；还没有三行 → 本 skill |
| **`system-analysis`** | 要一个数或一个判断 | 输入要的是数（有多少调用方）而不是需求 → 系统分析 |

## 边界

- 只回答「真正的问题是什么、值不值、往哪」，不回答「系统应该怎么做」——那是翻译的事。
- 提出方问不到时的降级（只做 1、3、4 步、把第 2 步标为假设）还没经主人裁定，用到时说一声再用。

## 自检（任一条破了就是失败）

- [ ] 原话一字未改，标了谁提的
- [ ] 对主人的每一句是断言，没有「你觉得」
- [ ] 三个问题全是历史行为，没有一个问意见或功能
- [ ] 查现成写的是查到的东西或「未查到」，没有把「没查」写成「没有」
- [ ] 三行加一句齐，第四句是可观察的判据
- [ ] 主人回来之前没写文件、没翻 EARS
