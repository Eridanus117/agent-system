# 需求洞察

工作里的需求从产品来，第一句永远是「解」（要支持 X）。动手翻译之前先把解翻回问题，判值不值得改、往哪改，并写下「解到什么样算解了」。这是 ISO 12207 的 6.4.1 业务或使命分析在 workCoding 里的规程，配套标准 29148 的需求获取一节。根本认识在 `需求分析.md`：需求方的陈述是待分析的输入，不是证据。

## 与 clarify 的差别

clarify 问的是主人自己；这里痒点来自提出方，agent 问不到，主人是中间人。所以 agent 的动作从「问」变成「备问题、收答案、下断言」，问的动作主人去做。另补 6.4.1 缺的那条产出：初步确认判据。

## 规程，五步

| 步 | 做什么 | 槽位里的实践 |
|---|---|---|
| 1 抄原话，判形状 | 原话一字不改，加谁提的。agent 判它是「解」还是「问题」，写断言草案：「提出方真正的问题是 P，不是 X」。同时判改动形状（改既有 / 从零新建 / 查数 / 只改规则或文档）并摆出要走的规程，**等主人确认路线再进下一条规程**（`方法论模型.md` 路线确认节） | clarify 工位 1，把解翻回问题 |
| 2 备三个问题 | 按草案生成三个问历史行为的问题：上次遇到怎么办的、现在怎么忍的、不做会怎样。主人拿去问提出方，把原话带回。不问「你想要什么」 | JTBD 切换访谈；29148 需求获取 |
| 3 查现成 | 现有模板、配置、运营手段能不能覆盖；查本库工作语境笔记「系统地图」与「领域术语」。雇主语境的 buy 即「用现有能力」 | clarify 工位 3；buy vs build |
| 4 收口三行加一句 | 真正的问题 / 值不值得改（含不改的路）/ 往哪个方向改。第四句「解到什么样算解了」：一条可观察判据。它是 6.4.1 的初步确认判据，直接喂 `需求翻译.md` 第 3 步的例子 | clarify 收口；12207 6.4.1 产出 |
| 5 留 | 原话、三个问答、三行加一句，进本库工作语境笔记「干系人与需求实例」；`需求翻译.md` 从这篇开始 | 本库工作语境笔记 |

## 产物样例

```
原话：运费模板要支持按省份设偏远附加（提：产品 A）
判形状：这是解。草案：真正的问题是新疆西藏的实际运费高于统一附加，商家在亏钱
问答：上次怎么办的 → 运营手动给新疆单补贴 ｜ 现在怎么忍 → 每周导表算差额 ｜ 不做 → 商家投诉，两家已流失
查现成：模板有「区域加价」字段但只到大区，不到省
三行：问题是偏远省份运费缺口由人工补 ｜ 值得改，每周两小时人工加已流失客户 ｜ 方向是省级附加表，排除大区字段细化因它被别的模块共用
判据：新疆单不再进补贴导表，连续两周
```

## 备选与不选理由

- Pre-mortem 泼冷水（clarify 工位 2）：大改动才做，小改动跳过，不占固定一步。
- 完整干系人访谈计划（29148 全套）：单人接单场景太重；三个历史行为问题够起步，答不出再加。

## 咬合

第 4 步的判据 → `需求翻译.md` 第 3 步例子 → 第 6 步自测验收。三条规程共用同一条判据，这就是 6.4.1 → 6.4.3 → 6.4.11 的追溯链。
