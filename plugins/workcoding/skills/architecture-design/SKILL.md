# 架构设计：先摆决定，再做攻防

在既有系统上设计一项新能力时，需求已经说明“要解决什么”，但还没有决定“系统应该成为什么样”。本规程补齐 6.4.4/6.4.5 的最小动作：把决定、候选、风险和证据缺口摆出来，主人确认后才进入实现。

**步骤真源在本文件；设计为什么采用这些动作见个人知识库 `notes/方法论模型.md`、`notes/实践备选库.md`。**

## 三条铁律

1. **先写决定，不先选技术。**
   先写要决定的业务对象、边界和判据；`sysTemplateType=9`、旧表、旧接口或尝试分支只能是证据，不是答案。
2. **事实、假设、选择分开。**
   `master` 或已验证回放是事实；未查明的内容写进未知；候选方案必须写出代价和失败后果，不用一个像样的实现细节掩盖未知。
3. **攻防结束仍等主人确认。**
   推荐方案不是授权。主人未确认前不改代码、不扩字段、不建表、不把草案写成正式规范。

## 五个工位

| 工位 | 干什么 | 判据 |
|---|---|---|
| **1 定决定** | 写清这轮要决定什么、不决定什么、谁受影响 | 一句话能说明决定对象和改变范围 |
| **2 摆基线** | 列出需求依据、现状证据、未知和约束；标明 `master`、尝试分支和外部依赖 | 每条事实有来源；每条未知有原因；没有把实现猜测写成事实 |
| **3 出候选** | 至少给出两个能落地的候选；逐项写接口、模型、存储、缓存、计费、失败和迁移影响 | 候选之间有真实取舍，不用“方案 A/B”制造假选择 |
| **4 做攻防** | 对每个候选各写支持、反对、最大风险和可逆性；缺数字时起 `system-analysis`，不自行编阈值 | 能指出什么证据会推翻推荐；没有只写推荐理由 |
| **5 收口** | 给出暂定推荐、放弃的替代方案、剩余未知和需要主人确认的决定 | 主人明确确认后，才把决定交给后续实现规程 |

## 产出：一份改动记录中的一节

不单独创建架构阶段文件。把以下内容放进当前改动记录的“方案”节；当前工作项的主文档只做导航和长期留痕：

```text
决定｜这轮要决定什么；本次不决定什么
基线｜已确认需求；master 现状；尝试分支；外部约束
未知｜尚未查明的事实；为什么未知；补证代价
候选｜候选 A、候选 B（必要时 C）；各自边界、代价、失败后果
攻防｜每个候选的支持、反对、最大风险、可逆性
推荐｜暂定选择；放弃的替代方案；推翻条件
确认｜请主人确认推荐和剩余未知；确认前不实现
```

## TUI 交互模式：决策卡，不要求主人回文件

默认把待决策信息直接放在当前对话里，不要求主人打开工作项或复制文件内容。每轮最多摆三张卡；一张卡优先，避免主人在 TUI 中维护长上下文。

### 助手发出的决策卡

```text
决策卡 D-001｜是否把 sysTemplateType=9 作为架构前提
建议｜暂不作为前提；保留为兼容性候选
选项｜A 直接沿用；B 独立身份；C 规范模型 + 适配层；D 暂缓
反对建议的理由｜会把一次实现取值固化成领域身份
请回复｜C / D / 否 D-001，理由=… / 查证 D-001，问题=…
```

卡片只保留决定、建议、选项、最大反对理由和回复格式；事实、未知和详细攻防已经写入改动记录，不要求主人从文件里捞出来。

### 主人的最短回复

- 当前只有一张卡：直接回复 `C`、`D` 或 `确认 C`；按卡片选项解析。
- 有多张卡：回复 `D-001=C；D-002=暂缓`。
- 否决建议：回复 `否 D-001，理由=…`；不得把普通质疑误记为确认。
- 要补证据：回复 `查证 D-001，问题=…`；转 `system-analysis` 或回需求规程。
- 部分确认：未点名的卡保持 `待确认`；不能因上下文顺带提及而自动确认。

助手收到回复后先用一行回显解析结果：`已记录 D-001=C；状态=confirmed；未批准实现`。回复有歧义时只追问歧义字段，不要求主人重贴整份方案。只有 `confirmed` 才能进入后续实现规程；`rejected`、`deferred`、`needs-evidence` 都不能越过主人确认门。

## 通道选择：TUI ask 是输入面，文件是持久面

- **默认走 TUI 的内置 `ask`**：它适合一到三张原子决策卡、选项确认、否决、暂缓和查证请求；当前 OMP 的 `ask` 只在 interactive mode 可用，不是需要另装的插件。
- **改动记录仍是持久真源**：助手从改动记录生成短卡，收到回复后回显解析结果并把裁定写回同一份记录；不要求主人复制文件内容到 TUI。
- **TUI 不可用或内容过长时走文本兜底**：使用本节的 `D-001=C`、`否 D-001，理由=…`、`查证 D-001，问题=…` 格式；文件用于长表格、证据和异步审阅，不作为日常决策输入门槛。
- **不能把两者混成两个真源**：TUI 回复是决定输入，改动记录是决定持久化；文件中的旧状态不能覆盖当前会话里已回显的新裁定。

## 与其他规程的边界

| 相邻 | 分界 |
|---|---|
| `workcoding` | 它负责判为“架构设计”并等主人确认路线；本规程负责方案动作 |
| `requirement-insight` / `requirement-translation` | 需求未收口先回需求规程；本规程不替需求方补业务答案 |
| `system-analysis` | 某个架构决定缺一个数或影响判断时触发；结论回填该决定 |
| `legacy-change` | 架构决定确认后，需要修改既有代码时进入；本规程不做代码分流和特征化测试 |
| `integration` | 代码改完接进系统时进入 |
| `grilling` | 主人明确要求独立压力测试时可单独使用；本规程自身已包含候选攻防 |

## 自检

- [ ] 决定没有被旧字段、旧表或尝试分支预先回答
- [ ] 事实、假设和未知分开
- [ ] 至少两个候选有真实取舍
- [ ] 每个候选都有反对意见、失败后果和可逆性
- [ ] 缺数字时没有编阈值，已触发 `system-analysis` 或标为未知
- [ ] 主人确认前没有实现、扩字段、建表或改正式规范
- [ ] 产出进入一份改动记录，没有为每个工位新建文件
