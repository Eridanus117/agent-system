# 系统分析

改动前某个决定缺一个数或一个判断——会波及哪些调用方、新路径慢多少、分流条件在真实流量里占多大比例——就起一次系统分析，限时两小时，出一行结论进那个决定。这是 ISO 12207 的 6.4.6 在 workCoding 里的规程；配套标准 IEEE 14764 软件维护的「修改分析」一节，系统分析在维护阶段就是影响分析。12207 要求的产出四条：要分析什么已写清、假设已记录、结果被核实、结果进了决定。

## 触发条件

不常驻。`遗留代码修改.md` 第 2 步写改法时卡住，或 `需求翻译.md` 第 3 步举不出例子，才起。产出的数必须挂一个决定（6.3.7 的规矩），那个决定就是第 5 步进的 ADR。

## 规程，五步

| 步 | 做什么 | 槽位里的实践 |
|---|---|---|
| 1 写问题和假设 | 一句话写要回答的问题，再写为回答它先假定了什么 | 12207 6.4.6 前两条产出 |
| 2 画影响草图 | 从改动点出发静态列两跳：谁调用它、它调用谁。用 IDE 调用层级或 jdeps 一类静态分析 | Feathers 影响草图 Effect Sketch；静态分析 |
| 3 抓运行证据 | 草图上拿不准的边，用 Arthas `trace` / `stack` 抓一条真实请求核实，顺带带回耗时。只抓拿不准的 | Arthas；基线测量 |
| 4 出结论 | 一行：数或判断 + 置信度 + 哪条假设没验证 | 12207 6.4.6 后两条产出 |
| 5 留 | 结论进该改动 ADR 的「背景」段（PR 正文）；第 2、3 步新发现的调用方与坑进本库工作语境笔记「系统地图」 | ADR；本库「系统地图」 |

## 产物样例

```
问：分流开关放 FreightCalc.calc 入口，有没有绕过它的调用方
假设：所有运费计算都走 calc
草图：调用 calc 的有 OrderService、QuoteService、BatchCalc（静态 3 个）
证据：Arthas stack 抓 1 条批量请求，BatchCalc 直接调 calcInner，绕过 calc
结论：有 1 个绕过入口的调用方，置信高；开关得放 calcInner，或 BatchCalc 单独接
留：ADR 背景；系统地图加一条「BatchCalc 绕过 calc 入口」
```

## 备选与不选理由

- 第 2 步：全量调用图工具（如 ArchUnit、依赖图生成）。不选：两跳够回答一次决定，全图是系统地图的事，按需累积。
- 第 3 步：压测。不选：单个改动的延迟估算一条 trace 够；压测属于 6.4.9 验证里的性能测试，需要时另起。
