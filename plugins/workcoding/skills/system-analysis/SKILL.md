# 系统分析：一个决定缺一个数，查一次，出一行

改动前某个决定缺一个数或一个判断——会波及哪些调用方、新路径慢多少、分流条件在真实流量里占多大比例——就起一次系统分析，限时两小时，出一行结论进那个决定。这是 ISO 12207 的 6.4.6 在 workCoding 里的规程；配套标准 IEEE 14764 的「修改分析」一节，系统分析在维护阶段就是影响分析。

真源在个人知识库 `notes/系统分析.md`（与标准的对照、备选与不选理由、裁决史、未解决）；步骤在本文。

## 为什么需要它

改既有代码时最贵的错不是写错，是「以为所有调用都走 calc」这种没核实的前提。前提错了，分流开关放错地方，新类别请求被兜底的 else 吃掉，回滚点也就没了。但把整个调用图画全又是另一种死法：两小时变两天，数出来了决定早做完了。所以只查决定缺的那一个数，草图两跳，证据只抓拿不准的边。

## 三条铁律

1. **每个数挂一个决定，写不出决定就不查。**
   第一行先写「这个数进哪个决定」；写不出来，说明不需要这个数。
   理由：6.3.7 的规矩——没有读者的量不测；查数是最容易无限扩大的活。
2. **先草图后证据，证据只抓拿不准的边；拿不出证据的边写「假设」。**
   静态两跳能定的边不用 Arthas；抓也只抓一条真实请求。
   理由：全量核实就是全量调用图，那是系统地图的事，按需累积。
3. **一行结论必须带置信度和没验证的假设；到两小时就出结论。**
   理由：结论是给决定用的，决定等不起；「置信中、假设 X 未验」比「再查两天」有用。

纠偏留痕：主人否了假设或草图，记「原写 A，裁为 B」在结论上面，不覆盖。

## 什么时候起，什么时候跳过

- 起：`workcoding` 为某个改动决定选中影响分析；`legacy-change` 摆改法或 `requirement-translation` 举例时遇到同类证据缺口。
- 普通静态查数、只读审查或资料比较直接查答；误加载本 skill 时回到原任务，不补一个路线确认。
- 静态证据足够时直接给结论；是否需要运行时核实由不确定的边决定，不由调用方数量决定。

## 五个工位

| 工位 | 干什么 | 槽位里的实践 |
|---|---|---|
| **1 写问题和假设** | 一句话写要回答的问题、它进哪个决定；再写为回答它先假定了什么 | 12207 6.4.6 前两条产出 |
| **2 画影响草图** | 从改动点出发静态列两跳：谁调用它、它调用谁。用 IDE 调用层级或 jdeps 一类静态分析 | Feathers 影响草图 Effect Sketch；静态分析 |
| **3 抓运行证据** | 草图上拿不准的边，用 Arthas `trace` / `stack` 抓一条真实请求核实，顺带带回耗时。只抓拿不准的 | Arthas；基线测量 |
| **4 出结论** | 一行：数或判断 + 置信度 + 哪条假设没验证 | 12207 6.4.6 后两条产出 |
| **5 留** | 结论进该改动改动记录的 ADR「背景」段（PR 正文）；工位 2、3 新发现的调用方与坑进工作语境笔记「系统地图」 | 改动记录；「系统地图」 |

看不到代码、跑不了 Arthas 时（例如在对话里被问），工位 2、3 写成「要主人在工作机上做的事」，格式不变，结论行写「待核实」。

## 产出：六行，没有别的

```
问｜<要回答的问题> → 进决定：<哪个决定>
假设｜<为回答它先假定了什么>
草图｜调它的：<一跳>；它调的：<一跳>；拿不准的边：<哪几条>
证据｜<Arthas 抓了哪条请求，看到什么 / 待主人在工作机上抓：命令>
结论｜<数或判断>，置信 <高/中/低>，未验证：<哪条假设>
留｜改动记录 ADR 背景段；系统地图加：<新发现>
```

例子：

```
问｜分流开关放 FreightCalc.calc 入口，有没有绕过它的调用方 → 进决定：开关放哪
假设｜所有运费计算都走 calc
草图｜调 calc 的：OrderService、QuoteService、BatchCalc（静态 3 个）；calc 调的：RemoteFeeLookup；拿不准的边：BatchCalc 是否直调 calcInner
证据｜Arthas stack 抓 1 条批量请求，BatchCalc 直接调 calcInner，绕过 calc
结论｜有 1 个绕过入口的调用方，置信高；开关得放 calcInner 或 BatchCalc 单独接；未验证：定时任务是否也调 calcInner
留｜ADR 背景；系统地图加「BatchCalc 绕过 calc 入口」
```

**只出这六行。不改代码、不写方案、不画全量调用图、不做压测。**

## 路由边界

| 相邻 | 它管什么 | 分界（可测） |
|---|---|---|
| **`workcoding`** | 按任务与风险选择规程 | 本 skill 只接具体改动决定的证据缺口；不重新确认已有路线，普通查数不先绕回路由 |
| **`requirement-insight`** | 需求是什么、值不值 | 未收口的问题交洞察；具体改动决定的影响证据缺口才进本 skill |
| **`legacy-change`** | 改代码 | 它的工位 2 卡住时起本 skill 一次，结论回它的改法里 |
| **`integration`** | 接进系统 | 本 skill 的草图喂它的集成面清单；变没变、接入顺序不在这里 |
| 压测、全量调用图 | 6.4.9 性能测试、系统地图 | 要的是性能曲线或整张图 → 不是本 skill，另起 |

## 边界

- 只回答一个决定缺的那一个数或判断；第二个问题另起一次。
- 两小时是硬上限，到点带着置信度出结论。

## 自检（任一条破了就是失败）

- [ ] 第一行写了这个数进哪个决定
- [ ] 假设单独成行，没混进结论里当事实
- [ ] 草图只有两跳，证据只抓了拿不准的边
- [ ] 结论一行，带置信度和未验证的假设
- [ ] 没改代码、没写方案、没扩成全量调用图
