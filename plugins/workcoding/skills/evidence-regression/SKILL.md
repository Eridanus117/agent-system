# 证据回归：母版改前采，改后逐字节比

代码写完后要回答两句：老流程一点没变，新流程是对的。agent 说「跑过了」不算证据，能进 diff 的文件才算。这是 workCoding 四个关注点里「证」的规程，实践是 Golden Master（又叫 Approval Testing，Feathers 一脉，Java 有 ApprovalTests 库），配套标准 ISO 29119 的测试记录要求。测试资产一律进代码仓，不进测试平台（2026-09-02 主人裁定）。

真源在个人知识库 `notes/证据回归.md`（与标准的对照、备选与不选理由、裁决史、未解决）；备选实践一排见 `notes/实践备选库.md` 槽位二；步骤在本文。

## 为什么需要它

`legacy-change` 的特征化测试锁的是一条入参，证明的是走读没编；一批真实请求上老路径有没有哪个分支被碰到，它证明不了。而 agent 最常给的证据是「我跑了一遍，没问题」——没有文件、没有 diff、三个月后无从复核。母版是改代码之前录下来的真实出入参，它把「没变」变成一个可以逐字节比的文件；新类别请求则拿需求翻译的例子当期望，把「是对的」也变成文件。

## 三条铁律

1. **证据是仓里的文件，「跑过了」不算。**
   母版文件、回放测试、比对结果三样进同一个 PR；不进测试平台。
   理由：能进 diff 的才能被审、被复核、被三个月后的人重跑。
2. **母版必须在改代码之前采；改后采的不是母版。**
   来不及在改前采的，用关着的分流开关或老版本代码采——老可执行路径 diff 为零时，关开关就是改前。含时间戳、随机 id 的字段先规整掉。
   理由：拿改后输出当母版，比的是自己和自己，永远通过。
3. **老类别逐字节一致，新类别对需求翻译的期望值；两类分开写。**
   理由：混在一起就分不清「没改坏」和「改对了」哪个没证到。

纠偏留痕：主人否了样本选择或规整规则，原话记在被否那行下面，不覆盖。

## 五个工位

| 工位 | 干什么 | 槽位里的实践 |
|---|---|---|
| **1 选样本** | 从 `requirement-translation` 的例子加真实流量里挑一批请求，覆盖新路径的每条 EARS 句和老路径的每个主要分支；每条标业务场景名 | 例子复用；等价类 |
| **2 采集母版** | 在改代码**之前**，用 Arthas 或日志把这批请求的出入参原样录下来，存成仓内文件（一请求一文件，JSON），这就是母版。含时间戳、随机 id 的字段先规整掉 | 录制回放；Golden Master |
| **3 回放比对** | 改完后，同一批请求喂新代码：老类别请求的输出必须与母版逐字节一致；新类别请求的输出与需求翻译工位 3 的期望值一致。写成单测，母版文件是测试的输入与期望 | ApprovalTests；特征化测试 |
| **4 影子流量（可选）** | 分流前，在预发让新老路径同时算、只返回老结果，异步比对差异。有副作用的路径不做 | 并行运行 Parallel Run；Scientist |
| **5 留** | 母版文件、回放测试、比对结果一起进同一个 PR；灰度期再按 `release-observe` 工位 3 用线上样本比对 | 测试资产入仓 |

工位 1、2 的样本清单与规整规则一次出完给主人否；工位 2 的采集在工作机上做；3–5 在改完之后。

## 产出：一张样本清单加一个仓内布局，没有别的

```
样本｜<场景名>：<请求要点> → 覆盖 <哪条需求句 / 老路径哪个分支>（每条一行，新老分开标）
采集｜改前，<Arthas 命令 / 日志来源>；规整：<去掉哪些字段>
布局｜samples/<模块>/<场景名>.request.json ｜ samples/<模块>/<场景名>.approved.json ｜ <回放测试类>
比对｜老类别 assertEquals(approved, actual) 逐字节 ｜ 新类别 assertEquals(<需求翻译的期望>, actual)
影子｜<做 / 不做，理由>
请否样本覆盖和规整规则；漏了哪个分支直接说。
```

例子：

```
样本｜首重续重-新疆-vip：模板 1032，新疆，3.2kg，vip → 新类别，覆盖需求句 1 ｜ 首重续重-广东：模板 1032，广东，3.2kg → 老类别，覆盖续重分支与「不在表中不加」｜ 首重-北京-cod：模板 2001，北京，0.8kg，货到付款 → 老类别，覆盖首重与 cod 分支
采集｜改前，Arthas watch FreightCalc calc '{params, returnObj}' -x 3 抓上面三条；规整：去掉 traceId、calcTime
布局｜samples/freight/首重续重-新疆-vip.request.json ｜ samples/freight/首重续重-新疆-vip.approved.json ｜ FreightGoldenMasterTest.java
比对｜老类别 assertEquals(approved, actual) ｜ 新类别 assertEquals(26, actual)（需求翻译例子）
影子｜不做：分流开关关着即老路径，样本够；有副作用的补贴导表不并行跑
请否样本覆盖和规整规则；漏了哪个分支直接说。
```

## 路由边界

| 相邻 | 它管什么 | 分界（可测） |
|---|---|---|
| **`legacy-change`** | 改代码；特征化测试 | 它锁一条入参证走读没编；本 skill 锁一批证老路径没变。工位 1 的走读入参是本 skill 样本之一 |
| **`requirement-translation`** | 例子变测试（6.4.11） | 它证新路径对；本 skill 的新类别比对直接用它的期望值，不另写期望 |
| **`release-observe`** | 线上灰度抽样 | 本 skill 是改前改后的仓内回放；灰度期的线上样本比对归它 |
| **`integration`** | 预发联调 | 联调是沿真实链路跑例子；回放是仓内单测，两码事 |
| 属性测试、对账、契约测试 | 备选 | 规则密集处补属性测试，结算类补对账，契约测试已排除（见 `实践备选库.md` 槽位二） |

## 边界

- 只回答「选哪些样本、怎么采、怎么比、放哪」，不回答「代码怎么改」和「放量放多少」。
- 不讲解 Approval Testing 本身；问「Golden Master 是什么」直接答。

## 自检（任一条破了就是失败）

- [ ] 样本覆盖了新路径每条需求句和老路径每个主要分支，每条有场景名
- [ ] 母版写明改前采，规整规则列了要去掉的字段
- [ ] 老类别与新类别分开，比对方式各写了
- [ ] 母版、测试、结果三样在同一个 PR 的布局里，没有测试平台
- [ ] 主人否过样本之前没采集、没写测试
