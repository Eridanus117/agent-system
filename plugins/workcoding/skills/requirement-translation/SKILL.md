# 需求翻译：一句一例，主人逐句否

外面来一句需求，agent 拿着就动手，人在它动手前无法判断它理解得对不对——与改代码的问题同构（`legacy-change`），解法也同构：**先翻成可验证的句子并配例子，人否，再动手。** 这是 ISO 12207 的 6.4.2 干系人需求与 6.4.3 系统需求在 workCoding 里的规程，第 6 步顺带覆盖 6.4.11 确认（自测验收）；配套标准 29148，用它检查产出。

真源在个人知识库 `notes/需求翻译.md`（与标准的对照、备选与不选理由、裁决史、未解决）；步骤在本文。

## 为什么需要它

`requirement-insight` 收口的三行加一句说的是「问题是什么、往哪走」，还不是「系统应该怎么做」。中间隔着一次翻译，而翻译最容易错在两处：一句话装了三件事，或者句子对了但没人能判它对不对。EARS 治第一处，例子治第二处。例子还有第二个用处——它就是后面走读代码时挑的那条真实入参、就是最后的验收测试，三处共用一条判据。

## 三条铁律

1. **没有例子的句子不算需求句。**
   每句配一条真实入参加期望输出；举不出例子说明这句还没想清，退回去，或起 `system-analysis` 去查。
   理由：可验证是系统需求最硬的属性，例子是最便宜的可验证。
2. **句中名词必须是主人原话或领域术语里的，不自造。**
   原话没有、术语表没有的词，先补术语再写句子。
   理由：无歧义靠的是同一个对象，不是措辞漂亮；主人看到不认识的名词只能说「看不懂」。
3. **主人逐句否之前不落盘、不变测试。**
   纠偏原话记在被否那句下面，不覆盖旧句。
   理由：例子变测试之后再改，代价是双份；被否的句子才是三个月后看得懂的部分。

## 先看要不要拆：大需求先按用例拆

一句话装不下的需求先拆用例，再对每个系统用例出 EARS 句。用例用 Cockburn 随意版：使用者、目标、主成功场景、扩展，标目标层级。判据一句：**一个使用者、一个目标、一次坐下来能完成** = 一个用户目标层用例；数目标就知道拆不拆。多个目标或多个使用者 → 概要层，先拆。规则密集的需求（运费类）补一张决策表，每条规则一行。

## 六个工位

| 工位 | 干什么 | 槽位里的实践 |
|---|---|---|
| **1 抄原话** | 需求原文一字不改，加谁提的、谁验收。这是干系人需求 | 29148 干系人需求 |
| **2 翻成 EARS 句** | 每条规则一句：「当 <触发> 时，系统应 <可观察行为>」或「若 <条件>，则系统应 <行为>」。五种句式：普适 / 事件驱动 When / 状态驱动 While / 非期望 If-then / 可选 Where | EARS（Mavin 2009） |
| **3 每句配例子** | 一条真实入参加期望输出。它就是 6.4.11 自测验收的判据，也是 `legacy-change` 走读时挑的那条入参 | Specification by Example（Adzic） |
| **4 人否** | agent 写「我读到的需求是这几句加这几个例子」，主人逐句否；纠偏原话记在句子下面，不覆盖 | 走查（IEEE 1028） |
| **5 留** | 主人否过之后：原话、EARS 句、例子、纠偏四样进工作语境笔记「干系人与需求实例」；EARS 句与例子进改动记录「拆」一节（PR 正文） | 改动记录 |
| **6 自测验收** | 第 3 步的例子原样变成测试；全部通过即自测验收完成。这就是 6.4.11 在 workCoding 里的全部，不另设规程 | Specification by Example 的可执行化 |

工位 1–3 一次出完给主人，工位 4 等主人，5–6 在主人否过之后。

## 产出：一张句子清单，没有别的

```
原话｜<一字不改>（提：<谁>；验：<谁>）
拆不拆｜<一个使用者一个目标，不拆 / 拆成 N 个用例：…>
1. 当 <触发> 时，系统应 <行为>。
   例：<入参> → <期望输出>
2. 若 <条件>，则系统应 <行为>。
   例：<入参> → <期望输出>
请逐句否；哪句不对写在那句下面，我不覆盖。
```

例子：

```
原话｜运费模板要支持按省份设偏远附加（提：产品 A；验：业务 B）
拆不拆｜商家配模板、系统算运费是一个目标，不拆
1. 当 目的地省份 在模板的偏远省份表中时，系统应 在基础运费上加该省份的附加金额。
   例：模板 1032，新疆，3.2kg → 基础 18 + 附加 8 = 26
2. 当 目的地省份 不在表中时，系统应 不加附加。
   例：模板 1032，广东，3.2kg → 18
3. 若 模板未配置偏远省份表，则系统应 按全局默认附加 5 元。
   例：模板 2001，新疆 → 基础 + 5
纠偏记录：第 3 句被否——没有全局默认，未配置即不加；原句保留在此，不覆盖。
```

**主人逐句否之前：不写文件、不写测试、不走读代码。**

## 出手前用 29148 自查

每句过九条属性里最常破的四条：可验证（有例子就算过）、单一（一句只说一件事）、无歧义（名词都在原话或术语表）、必要（删掉这句会不会有人做错决定）。破一条退回工位 2。

## 路由边界

| 相邻 | 它管什么 | 分界（可测） |
|---|---|---|
| **`requirement-insight`** | 把解翻回问题，收口三行加一句 | **状态**：还没有三行加一句 → 洞察；有了 → 本 skill |
| **`system-analysis`** | 要一个数或一个判断 | 工位 3 举不出例子、缺一个数时起它一次，回来继续 |
| **`legacy-change`** | 改代码 | 例子在这里是期望输出；在它那里是走读入参。主人否过句子之后才轮到它 |
| **`evidence-regression`** | 证明老流程没变 | 本 skill 的测试证新路径对（6.4.11）；母版回放证老路径不变（6.4.9），两码事 |

## 边界

- 只翻「系统应做什么」，不翻「怎么实现」；句子里出现类名、表名、字段名就是越界。
- 不讲解 EARS 或用例方法本身；问「EARS 有几种句式」直接答，不进规程。

## 自检（任一条破了就是失败）

- [ ] 原话一字未改，标了提出方与验收人
- [ ] 每句一件事，每句都有一条入参加期望输出
- [ ] 句里没有原话与术语表之外的名词，没有类名、表名、字段名
- [ ] 写了拆不拆和判据（一个使用者一个目标）
- [ ] 主人否之前没写文件、没写测试
