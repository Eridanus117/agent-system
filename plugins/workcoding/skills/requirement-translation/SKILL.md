# 需求翻译

外面来一句需求，agent 拿着就动手，人在它动手前无法判断它理解得对不对——与改代码的问题同构（见 `遗留代码修改.md`），解法也同构：先翻译成可验证的句子并配例子，人否，再动手。这是 ISO 12207 的 6.4.2 干系人需要与需求定义、6.4.3 系统需求定义在 workCoding 里的规程，第 6 步顺带覆盖 6.4.11 确认（自测验收）；配套标准 ISO/IEC/IEEE 29148，用它检查产出。

## 上面一层：大需求先拆用例（2026-09-02 加）

一句话装不下的需求先拆用例，再对每个系统用例出 EARS 句。用例用 Cockburn 随意版：使用者、目标、主成功场景、扩展，标目标层级。判据一句：**一个使用者、一个目标、一次坐下来能完成** = 一个用户目标层用例；数目标就知道拆不拆。多个目标或多个使用者 → 概要层，先拆。规则密集的需求（运费类）补一张决策表，每条规则一行。备选见 `实践备选库.md` 槽位一。

## 规程，五步

| 步 | 做什么 | 槽位里的实践 |
|---|---|---|
| 1 抄原话 | 需求原文一字不改，加谁提的、谁验收。这是干系人需求 | 29148 干系人需求 |
| 2 翻成 EARS 句 | 每条需求一句：「当 <触发> 时，系统应 <可观察行为>」或「若 <条件>，则系统应 <行为>」。句中名词必须在本库工作语境笔记「领域术语」里有，没有的先补术语。这是系统需求，最硬的属性是可验证 | EARS（Mavin 2009，五种句式：普适 / 事件驱动 When / 状态驱动 While / 非期望 If-then / 可选 Where） |
| 3 每句配例子 | 一条真实入参加期望输出。它就是 6.4.11 自测验收的判据，也是 Feathers 流程第 1 步走读时挑的那条入参 | Specification by Example（Adzic） |
| 4 人否 | agent 写「我读到的需求是这几句加这几个例子」，人逐句否；纠偏原话记在翻译下面，不覆盖 | 走查（IEEE 1028） |
| 5 留 | 原话、EARS 句、例子、纠偏四样进本库工作语境笔记「干系人与需求实例」；EARS 句与例子进 PR 正文 | ADR 归档 |
| 6 自测验收 | 第 3 步的例子原样变成测试；全部通过即自测验收完成。这就是 6.4.11 确认在 workCoding 里的全部，不另设规程 | Specification by Example 的可执行化 |

## 产物样例

```
原话：运费模板要支持按省份设偏远附加（提：产品 A；验：业务 B）
1. 当 目的地省份 在模板的偏远省份表中时，系统应 在基础运费上加该省份的附加金额。
   例：模板 1032，新疆，3.2kg → 基础 18 + 附加 8 = 26
2. 当 目的地省份 不在表中时，系统应 不加附加。
   例：模板 1032，广东，3.2kg → 18
3. 若 模板未配置偏远省份表，则系统应 按全局默认附加 5 元。
   例：模板 2001，新疆 → 基础 + 5
纠偏记录：第 3 句被否——没有全局默认，未配置即不加；原句保留在此，不覆盖。
```

## 用 29148 检查产出

每句过九条属性里最常破的四条：可验证（有例子就算过）、单一（一句只说一件事）、无歧义（名词都在术语表）、必要（删掉这句会不会有人做错决定）。破一条退回第 2 步。无歧义那条用 `需求分析.md` 的「十类模糊模式审查清单」逐句过。

## 备选与不选理由

- 第 2 步：Gherkin 的 Given / When / Then、用户故事。不选：它们描述场景，不描述规则；运费类需求是规则。OpenSpec 的 `Requirement / Scenario` 格式可作第 5 步的落盘形态之一。
- 第 3 步：等价类划分列全量用例。不选：翻译阶段只要一条能判对错的例子，全量用例是 6.4.9 验证的事。
