# 方法资产模型

## 人话结论

一套方法的共同正文只保存一次，Codex 与 Claude 的真实差异分开保存。Git 中的来源文件是可恢复的权威；安装缓存和用户配置只是某台电脑上的运行状态。

本轮先允许 Agent 自动加载 `grilling`，但这不等于允许它自动开始问询。用户直接请求或明确接受建议后才能进入方法，手动入口必须保留；运行端最终显示的命令名仍待后续 Plugin 实验验证。

`grilling` 只是第一个试验样本，与期待的完整“升级思考”仍有差距。下面的物理目录也只是待验证候选，不是已经成立的架构。

## 本文使用的状态

| 状态 | 含义 |
| --- | --- |
| 产品合同 | 已确定的用户可见行为；实现不能自行改写 |
| 已批准试验输入 | 首次试验从这里开始，但可以被运行证据推翻 |
| 待验证 | 当前没有足够证据，不能写成事实 |
| 失败回退 | 待验证项失败后采用的可逆方向 |

本文把 Codex 与 Claude 统称为**运行端（Provider）**。Plugin manifest 指 **Plugin 清单文件**，Marketplace 指 **发现与安装目录**，conformance 指 **符合性证据**。

## 各对象的责任

| 对象 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| [产品行为合同](https://github.com/Eridanus117/agent-system-foundry/blob/main/product/method-intervention.md) | 普通路径、方法建议、同意、拒绝、降级、换方法和退出等用户可见规则 | Plugin 目录、清单字段和安装命令 |
| 共同方法正文（Skill） | 方法步骤、事实与决定的分工、确认和退出语义 | 运行端安装、发现目录和用户启用状态 |
| 运行端元数据 | Codex 或 Claude 特有的调用、显示、依赖和兼容差异 | 判断用户是否已经同意，或复制另一份共同正文 |
| Plugin 清单文件 | 安装单元的身份、版本和组件入口 | 成为产品行为合同 |
| 发现与安装目录 | 找到 Plugin、定位来源并表达安装政策 | 拥有 Plugin 内容 |
| 来源记录 | 上游仓、提交、文件、许可证和本地修改 | 自动证明本地改造正确或有价值 |
| [符合性证据](conformance.md) | 分层记录来源、格式、安装、生命周期、行为和投入产出证据 | 用低层检查替代高层结论 |
| 安装缓存和用户配置 | 保存某个运行端在某台电脑上的派生状态 | 成为可编辑来源或跨电脑权威 |
| GitHub Issue | 保存目标、决定、依赖、进度和证据链接 | 成为可执行包、产品合同或可信知识本体 |

责任按上表单向引用：产品合同规定行为，共同正文实现方法，运行端文件负责包装，符合性证据检查结果。缓存、配置和 Issue 都不能反过来成为资产正文。

## 只保存一次与必须分开

共同方法正文只有一个可编辑来源。一个安装版本还必须自包含它运行所需的许可证、来源说明和相对资源，不能依赖仓外路径或某台电脑的缓存。

以下差异必须如实分开：

- Codex 与 Claude 的 Plugin 清单字段；
- 调用控制、显示信息和运行端依赖；
- 发现与安装目录中不能共享的字段；
- 各运行端的安装、校验、卸载和回滚证据。

“分开保存差异”不等于复制共同正文。若两个运行端最终需要两个安装包，它们也应由同一共同来源产生，不能手工维护两份方法语义。

## 自动调用与用户同意

这里有两个不同问题：

1. **运行端是否允许 Agent 加载 Skill？** 这是调用配置控制的能力。
2. **Agent 是否可以开始方法问询？** 这是产品合同控制的行为。

当前状态是：

- **产品合同**：用户直接请求方法，或在 Agent 给出一次建议后明确接受，才允许开始问询。
- **产品合同**：任务复杂、命中关键词或 Agent 认为方法有用，都不构成同意。
- **当前装配来源**：daily profile 从固定的 `vendor/mattpocock/skills` 来源装配 `grilling`。
- **当前入口**：两个运行端保留手动调用 `grilling` 的入口。
- **来源边界**：当前使用 Matt 的原版 Skill，不在本仓维护本地 Fork。
- **待验证**：Claude 与 Codex 最终显示的命令是否正好是 `/grilling`、`$grilling`，还是带有 Plugin 命名空间。
- **失败回退**：哪个运行端守不住同意边界，就先把哪个运行端收紧为只能由命令进入，并记录增加的用户步骤。

因此，配置字段只能证明 Agent 有没有加载能力，不能证明用户已经同意，也不能单独证明方法行为合格。

## 当前物理来源

`grilling` 不再作为本仓 Plugin 发布，也不再复制一份本地正文；当前由 daily profile 直接引用 Matt 的固定 vendor 来源。

```text
vendor/mattpocock/
└── skills/
    └── grilling/
        ├── SKILL.md
        └── agents/
            └── openai.yaml
```

共同正文只保留在 vendor 来源；两个运行端的装配入口由 profile 与各自运行端处理，不由本仓 Marketplace 再包一层。

## 已确定、待验证与回退

| 主题 | 当前状态 | 失败回退 |
| --- | --- | --- |
| 共同正文只保存一次 | 产品合同之外的资产决定，已经确定 | 不回退到两份手写正文 |
| 首次试验允许 Agent 自动调用 | 已批准试验输入 | 只收紧不能守住同意边界的运行端 |
| 两个运行端保留手动调用入口 | 已批准试验输入；具体命令名待验证 | 接受运行端要求的命名空间，并如实记录额外步骤 |
| 一个目录同时服务 Codex 与 Claude | 待验证 | 保留共同来源，生成两个自包含安装包 |
| Claude 扩展字段可被 Codex 安全接受 | 待验证 | 把运行端特有包装放入各自产物 |
| 两个运行端共享一个发现目录文件 | 待验证 | 保留两个运行端各自的发现投影 |
| `grilling` 产生正向投入产出 | 待验证 | 缩小触发范围、改为命令入口或退役 |
| `grilling` 能代表完整“升级思考” | 当前没有证据，且负责人已指出存在差距 | 试用后把缺口作为独立方法需求分析 |

## 何时升级资产模型

当前不建设生成器、两个全文包或整仓 Fork。只有出现以下证据之一，才重新比较这些方案：

- 第二个真实方法资产出现，并产生稳定、重复的包装工作；
- 单目录在任一运行端无法安装或可靠工作；
- 路径级上游回顾的实测成本高于整仓维护；
- 手工同步已经造成可观察的遗漏或语义漂移。

“未来可能扩展”本身不是升级理由。每次升级都要同时说明收益、首次成本、持续判断成本和可逆路径。
