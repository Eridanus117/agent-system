# 把念头变成判断

主人的念头永远以「解」的形式出现（「我想建个 X」），X 已经预设了问题、解法和值得。本 skill 只做一件事：把 X 翻回问题，再判断该不该解。agent 是提问方，不是产出方。为什么这样设计、试过什么失败了，见知识库规程笔记「念头判断」。

## 三条铁律

1. **给断言，不给问句。** 写「这个仓是 X」，不写「你觉得这个仓是什么」。主人判「这句不对」比答「你想要什么」快十倍；问开放题只会得到「我的认知有点不太够」。
2. **草案和主人站在同一个具体对象上，不用黑话。** 不用占位符（X、Z）、自造词、流程代号；把具体对象贴出来——主人的原话、一条真实请求、一个文件名——整句说话。主人说「看不懂」不是嫌长，是没在同一语境。
3. **纠偏本身要留痕**：记「我说 A，主人说不是，是 B」，不只留最新版。被否掉的路径才是三个月后看得懂的那部分。

## 四个工位（针对当下这个念头现生成，不照念）

| 工位 | 干什么 | 用什么 |
|---|---|---|
| 1 把解翻回问题 | 找出真正卡住的是什么 | 问历史行为（上次撞到时你怎么办的？现在怎么忍过来的？），不问意见；5 Whys |
| 2 泼冷水 | 找出这事会怎么砸 | Pre-mortem：假设半年后彻底失败，回头看为什么；列 4–5 条按可信度排，优先采信有历史证据的 |
| 3 先找名字 | 该不该自己做，别反复发明 | 这个问题和这个解法业界叫什么、谁已经解过、他们怎么失败的；然后才是有没有现成的能直接用。agent 代跑，主人零成本；写不出名字本身是信号 |
| 4 收口 | 出结论 | 三行 |

载体：agent 写断言式草案 → 主人纠偏 → 重复到主人不想改了。

## 产出：三行

```
1｜真正的问题：不是「<念头原话>」，而是 <翻译后的问题>（业界叫 <名字>；查过没找到就写「查过，未找到对应名」）
2｜值不值得解：<值得/不值得/先不解> —— <理由，含发生频率与已付代价>
3｜往哪个方向解：<方向>，沿用或参照 <已有解法> —— <排除掉的方向及原因>
```

名字那格不许空着；没查就给结论算失败。

## 两个出口

- **不建、先不解**：三行原样写进 desk 收件箱一行（`记录.ts --append`），含理由。到此结束，不建目录、不开 change。
- **建**：在本仓的 issue tracker 建一条 issue，标题是第 1 行的问题，正文是三行；tracker 没配置就进 desk 仓 Issues。标签留给 tracker 自己的词表，本 skill 不定。这条 issue 是后面对齐的把手：结论被推翻时在它下面追加一条，再重跑本 skill，不许直接进下一步。

## 边界

- 只管「我想建个 X」这类念头；「这个 bug 烦我」不套。
- 只答「该不该做」，不答「做成什么样」；那是下一步（grill）的事。
- 对象已成形、主人要压力测试的，是 grilling 不是这里。

## 自检（任一条破了就是失败）

- 没有产出三行之外的文件；建的话只多一条 issue
- 主人没说过「我不知道你在干嘛」
- 问题是现生成的，草案里没有占位符、自造词、流程代号
- 第 1 行带名字或「查过，未找到对应名」
