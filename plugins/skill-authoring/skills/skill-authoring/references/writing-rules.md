# 正文怎么写

来源：Anthropic 的 skill 写作指南、Matt Pocock 的 writing-for-agents、superpowers 的 writing-skills 里对本工作区仍成立的部分（取舍见 vendor-adoption，SKILL.md 直接链到）。三条硬合同定在 ADR-0006：术语只用有出处的业界词；骨架只必有两节；正面陈述目标行为，禁令紧跟正面句。

## 骨架：必有两节，其余按需

必有：

1. **什么时候用**：触发与不触发各一段。不触发那段写清该归谁。
2. **步骤**：有序，每步末尾带完成判据，能分辨「做完没做完」。先磨清晰度，再看要求量。

按需，有内容才加：

- **产出**：会留下什么文件或记录。
- **出口**：到此为止、后面归谁；一个出口就写一个。
- **为什么在哪**：指向 issue、ADR、词汇表；论证留在那里，正文不重讲。

三类节不再写，它们的内容各有真源：「路由边界」表归路线真源与入口（ADR-0004）；「自检」归每步末尾的完成判据；「验证状态」归 `evals/README.md` 的实跑记录。

## 术语：只用有出处的业界词

- 每个术语都能在标准、书、知名框架或项目文档里查到。中文用通行译名，首次出现附英文原词与出处，例：「阶段（stage，Cooper 的 Stage-Gate）」。
- 查不到出处的概念不起名，用平语句子说清它是什么，例：「改旧代码时才开的活动」。
- 本仓已定的词在 `plugins/CONTEXT.md`，正文按它用；要加新词先在词汇表加一条，标题带英文与出处。
- 「自造」标记没有了：`plugins/tests/skills.test.ts` 守着 SKILL.md 与词汇表。

## 分层：实践与规程

实践（practice）skill 讲怎么做一件事（grilling、tdd、特征化测试这类），一条实践只在一个文件里。规程（procedure）skill 按活动点名实践，一行组合，正文不内联实践的做法。两个词的定义在词汇表。目录按层分：`plugins/practices`、`plugins/flow-steps`、`plugins/flow`（ADR-0006；目录随第二、三批落地）。

## 写法

- 祈使句写步骤；解释为什么一句就够。
- 正面陈述目标行为：先写要做成什么样。禁令只留硬护栏，也就是有诱惑走捷径时才会犯的错；每条禁令紧跟一句正面目标，例：「不抄目录结构；写『去查』并给出查的命令」。
- 输出有固定形状的，骨架加一对输入输出例子放 `references/`，正文只引用；例子用用户原话里的对象，代替 X／Y 占位符。
- 按错法选表达形式：容易找借口走捷径的，写规则再列一张「常见借口对事实」的表；输出形状错的，给配方与模板；漏项的，列出必须填的项；看情况才做的，写成可观测的条件句。
- 能用脚本或测试机械保证的，写成脚本或测试，文字只说去哪跑。
- 环境是真相源：目录结构、命令帮助、配置项写「去查」，给出查的命令。
- 想清楚类的 skill（clarify、grill 这类）加三条：一轮只递一题；说平语，代替黑话；先给具体例子再问。

## 写完过一遍：四条

1. 单一真相源：同一句话只在一处。
2. 环境本身是真相源：能一条命令查到的写查法。
3. 逐行查相关：这一行不在，agent 会做错什么？答不上来就删。
4. 逐句猎无效句：模型默认就会做的，删整句而不是改词。

## 描述

一句话，「做什么、什么时候用」，给人看，中文加英文尾。触发由路线真源里的路由句决定（ADR-0004），描述里只写事实，省掉「一律」「必须先」这类路由句。

## 长度

正文不超过 500 行是硬线；软线是「每一行都在，且没有一行重复」。真正的步骤留着，长度靠「写完过一遍」的四条来收。
