# 改旧代码

第 5 阶段里改旧代码时才开的活动，开不开在第 4 阶段的门上定；名字取 Feathers《修改代码的艺术》的遗留代码修改算法（legacy code change algorithm）。做法在两条实践里：`characterization-test`、`sprout-method`；这里只点名和定顺序。用词按 `plugins/CONTEXT.md`：阶段、活动、证据。

## 什么时候用

用：`flow` 第 4 阶段门上开了它——要改的旧代码没有测试，或注释与实现对不上、牵连不清；主人说「按 Feathers 走」。

不用：从零新建，门上写了「从零新建，不开改旧代码的活动」——直接请主人敲 `/implement`；主人要原地修一处低风险错误——标准变更，直接改。

## 步骤

1. 先锁现状：按 `characterization-test`，拿一条真实入参走读，写成带注释的测试，把走读清单、假设和改法三句摆给主人否——新逻辑放哪个新方法或新类；哪个开关开启且入参哪个字段命中时转去新方法；开关关闭或未命中时走哪个原入口。开关用主人指明的现有配置，没指明就列为待确认。否之前生产代码不动。完成判据：主人对走读与改法三句说了「对」。
2. 再萌芽：按 `sprout-method`，新逻辑放新方法或新类；既有代码只改一处——旧方法第一行加分流（新方法要拿老结果当输入时放旧语句全部之后也行，不插在旧语句之间），开关开启且入参命中的判断就在这一处，其余落回旧体，旧体一句不动。完成判据：同一条入参，开关关得老结果、开且命中得新结果、开但未命中不变，三条有结果或标「未验证」。
3. 交出去：走读、改法与主人的纠偏原话进 PR 正文「做了什么」，三条验证进「怎么验证的」；要接进系统时接着开 `system-integration`。完成判据：PR 正文里能找到走读、改法和三条验证。
