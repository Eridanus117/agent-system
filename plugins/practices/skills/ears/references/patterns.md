# 五种句式与一对输入输出

## 五种句式

| 句式 | 形状 | 例 |
|---|---|---|
| 普适 ubiquitous | 系统应 <行为> | 系统应给每条工单一个唯一的工单号。 |
| 事件驱动 event-driven | 当 <触发> 时，系统应 <行为> | 当一条工单被关闭时，系统应向提单人发送关闭通知。 |
| 状态驱动 state-driven | 在 <状态> 期间，系统应 <行为> | 在工单处于待客户回复期间，系统应暂停计算关闭时效。 |
| 非期望行为 unwanted behaviour | 若 <条件>，则系统应 <行为> | 若关闭通知发送失败，则系统应保持工单为已关闭并记录发送失败。 |
| 可选特性 optional feature | 若配置了 <特性>，系统应 <行为> | 若配置了自动归类，系统应在工单创建时按标签规则打标签。 |

复合句（complex）是两种以上叠在一起：「在工单处于待客户回复期间，当客户回复时，系统应…」。先试拆，拆不开再叠。

## 输入（原话与词汇表）

> 词汇表：工单、标签、客服、提单人、关闭、关闭通知。
> 原话：「重复工单要能批量关，而且关掉要通知提单人，通知失败不能卡住关闭。」「TicketService 调 notify_queue 发通知。」

## 输出

```
1. 当客服选中带同一标签的多条工单并执行关闭时，系统应把这些工单全部置为已关闭。（事件驱动；「重复工单」按假设解释为带同一标签的工单，请主人否）
2. 当一条工单被关闭时，系统应向提单人发送关闭通知。（事件驱动）
3. 若关闭通知发送失败，则系统应保持工单为已关闭并记录发送失败。（非期望行为）
4. 原话「TicketService 调 notify_queue 发通知」说的是实现；它要的行为已在第 2 句，不另写。
```

要点：一句一个「系统应」；名词全在词汇表；类名与队列名不进句子；解释过的地方标「假设」交主人否。
