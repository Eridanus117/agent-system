# 测试驱动开发（tdd）

来源：Matt Pocock 的 `tdd`（github.com/mattpocock/skills，revision 6acc160，MIT，许可全文见 `plugins/practices/LICENSE-mattpocock`），按 ADR-0007 复制入库改写。TDD 与红绿循环出自 Beck《测试驱动开发》；接缝（seam）出自 Feathers《修改代码的艺术》。`implement` 内含本实践；重构不在本循环里，归审查阶段的 `code-review`。与原版的差别：补了「跑不了就标未验证」（本工作区的证据规矩）、「只补测试不改行为归 `legacy-change`」、「拿耦合实现的测试当样板先指出不照抄」（评测里对照组照抄的缺口）三处；原版「每节每轮都看」「codebase-design 是参考不是会话」两句并进了第 1、2 步。

## 什么时候用

用：主人要测试先行地做功能或修 bug，说「TDD」「红绿」「先写测试」，或要集成测试；规程在实现阶段点名。

不用：只是给既有代码补测试、不改行为，那是特征化测试，归 `legacy-change`；主人拿着一条耦合实现的测试当样板要「照着再写几条」，先按第 2 步把它指出来，不照抄。

## 步骤

1. 定接缝，写下来，请主人确认。先读 `CONTEXT.md`（有的话）和碰到的那块的 ADR，测试名和接口用词跟项目的领域语言走。接缝是观察行为而不伸手进内部的那条公共边界；测试只放在接缝上。动笔前列出要测的接缝，一题问主人：「公共接口是哪个，测哪几条接缝？」没确认的接缝不写测试：测不完所有东西，先定接缝才能把力气落在关键路径和复杂逻辑上。接口本身的形状（模块多深、接缝在哪、暴露什么）有疑问时，用 `codebase-design` 的词来谈。完成判据：接缝清单主人说了「对」。
2. 认得好测试和坏测试。好测试穿公共接口验证行为，读起来像一句规格（「user can checkout with valid cart」），内部全换掉它也不动；例子见 [tests.md](./references/tests.md)，mock 的边界见 [mocking.md](./references/mocking.md)。三种坏测试当场改掉：
   - **耦合实现**：mock 内部协作者、测私有方法、从旁路验证（查数据库而不是走接口）。信号：重构没改行为，测试却挂。
   - **同义反复**：期望值照着代码的算法重算（`expect(add(a, b)).toBe(a + b)`、手工按同一算法推出来的快照、常量等于自己），按构造必过。期望值来自独立的真源：已知正确的字面值、算好的例子、spec。
   - **横切**（horizontal slicing；出处：Matt Pocock 的 tdd）：先写完所有测试再写所有实现。批量测试验证的是想象中的行为，测的是形状不是用户可见的行为，对真实改动不敏感，还在理解实现之前就锁死了测试结构。改成竖切（vertical slice；出处同上，敏捷通行的用法）：一个测试、一个实现、再来，每个测试是一颗曳光弹（tracer bullet；出处：《程序员修炼之道》），回应上一轮学到的东西。
   完成判据：每条测试都能指出它测的接缝和期望值的独立来源。
3. 先红后绿。先写失败的测试，再写刚好让它过的代码；不预支后面的测试，不加投机的功能。完成判据：新测试跑过一次红、一次绿；跑不了就说明跑不了，标「未验证」。
4. 一次一片。一个接缝、一个测试、一个最小实现是一个循环；做完说下一片是什么。完成判据：每轮只多一片。
5. 重构不在循环里。红到绿做完，重构留给审查阶段的 `code-review`。完成判据：绿了以后没有顺手重写。

## 产出

主人确认过的接缝清单；一对一对的测试与实现。
