# 影响草图（effect-sketch）

影响草图（effect sketch）出自 Feathers《修改代码的艺术》第 11 章：从要改的地方出发，画出改动会影响到的方法、变量与调用方。这里固定两跳，够回答一次决定。用词按 `plugins/CONTEXT.md`。

## 什么时候用

用：改动前要知道会波及谁——分流开关放哪、哪些调用方要一起改、哪些测试要跑；`impact-analysis`、`integration` 这类活动点名；主人说「画一下影响」「谁在调它」。

不用：证据已经贴齐、只要一个数（「有几个直接调用方」），直接答数与文件名，不套草图；要的是整张调用图或依赖图，那是系统地图，用 jdeps、ArchUnit 这类工具另起。

## 步骤

1. 定改动点。写出要改的那个方法或字段，草图从它出发。完成判据：改动点是一个能在代码里定位的名字。
2. 静态画两跳。往上一跳：谁调它（IDE 的调用层级、按符号名 `grep`）；往下一跳：它调谁。同一个类里别的入口也看一眼——有没有绕过改动点、直接调它里面那层方法的调用方，这种绕过就是开关放错地方时漏掉的那条路。完成判据：每条边都能指出在哪个文件看到的；绕过改动点的调用方（如果有）在草图上。
3. 标拿不准的边。手头没有代码的模块、反射与动态代理、定时任务与消息消费者、配置里注册的处理器：写成「待核实」，并写清什么能核实——一条 `grep`，或抓一条真实请求看调用栈（JVM 上 Arthas `stack`，别的运行时用它自带的追踪器）。只核实拿不准的边，静态能定的不抓。完成判据：每条待核实的边都带一个核实方法。
4. 事实与假设分开写。从代码读到的边是事实；推断的写成假设，连「所有计算都走这个入口」这种默认前提也写出来。完成判据：草图里没有一条边既没标来源也没标假设。

## 产出

一张两跳草图：调它的、它调的、绕过它的、待核实的边，各带来源或核实方法；形状与例子见 [sketch.md](./references/sketch.md)。新发现的绕过与调用方写进目标仓自己的文档（CLAUDE.md 或 docs），下次不用再画。
