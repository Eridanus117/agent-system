# ADR 的格式与什么时候写

来源：Matt Pocock 的 domain-modeling（ADR-FORMAT.md，revision 6acc160），MIT。仓里已有 ADR 约定（比如本仓 `docs/adr/README.md` 定的 MADR 模板）就沿用仓里的，不另起一套；下面是没有既定约定时的默认。

## 位置与编号

ADR 放 `docs/adr/`，顺序编号：`0001-slug.md`、`0002-slug.md`。目录懒建，第一份 ADR 要写时才建。编号取目录里最大的加一。

## 模板

```md
# {决定的短标题}

{一到三句：背景是什么、定了什么、为什么。}
```

就这么多。一份 ADR 可以只有一段；价值在于记下**做过这个决定**和**为什么**，不在于填满节。

## 按需加的节

只在真有价值时加，多数 ADR 不需要：

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决定会被重审时有用。
- **Considered Options**：被否的备选值得记住时。
- **Consequences**：下游影响不明显、需要点出来时。

## 什么时候提议写 ADR

三条同时成立才写：

1. **难回头**：以后改主意代价明显。
2. **不看背景会奇怪**：以后的读者看到代码会问「当初为什么这么做」。
3. **真有取舍**：有真实的备选，出于具体理由选了一个。

容易回头的不写，回头就是了；不奇怪的没人会问为什么；没有备选的除了「做了显然的事」没什么可记。

### 够格的例子

- **架构形状。**「用 monorepo。」「写模型事件溯源，读模型投影进 Postgres。」
- **context 之间的集成方式。**「Ordering 与 Billing 之间走领域事件，不走同步 HTTP。」
- **带锁定的技术选型。** 数据库、消息总线、认证供应商、部署目标。不是每个库都算，只算换掉要花一个季度的那些。
- **边界与范围。**「客户数据归 Customer context 所有，别的 context 只按 ID 引用。」明写的「不做」和「做」一样值钱。
- **刻意偏离显然路径。**「用手写 SQL 不用 ORM，因为 X。」凡是一个合理的读者会以为相反的地方，记下来能拦住下一个人把它「修好」。
- **代码里看不见的约束。**「合规要求不能用 AWS。」「合作方 API 合同要求响应 200ms 以内。」
- **否掉的备选，当否的理由不显然时。** 考虑过 GraphQL、出于微妙理由选了 REST，记下来，否则六个月后有人会再提一遍。
