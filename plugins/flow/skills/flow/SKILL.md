# 改动落地的路线

用词按本仓词汇表（`plugins/CONTEXT.md`）：来往、门、步、可选步。哪种来往、开场那一句、等不等主人，由常驻规则定；这里只管判为改动落地之后的事。

## 什么时候用

用：常驻规则判为改动落地；或主人开场直接敲了段里的 skill（`/grill-with-docs`、`/to-spec`、`/to-tickets`、`/implement`）——先读这里，再跑那条 skill。

不用：要答案、小改动，按常驻规则做，不读这里。一个例外：小改动做到一半发现要在做法之间选，改判为改动落地，回到这里从第 2 段进。

## 步骤

### 开场后的可撤动作

issue、票、PR 开场时不等主人，按顺序做，做完直接给起始段门口那条消息：

1. 绑定。`orca worktree show --worktree issue:N` 查这个 issue 有没有活着的 worktree（只按编号查，查到的核对是不是同一个仓）：已有就提醒主人，不再开；没有就 `orca worktree set --worktree active --issue N`。PR 绑它关联的 issue。会话不在 Orca worktree 里（比如站在工作区根）就跳过绑定。
2. 读它最后一条停靠记录（issue 下标题前缀 `### 停靠` 的评论；公开仓的事在 desk 里对应的父 issue 上），从「下一步」接着做；复用原范围内的决定，已有授权不因换会话失效，也不扩大到新动作。
3. 定起始段：机会 issue → 第 2 段；需求 issue 或票 → 第 4 段；PR → 第 6 段；主人指定「从第 N 段进」→ 第 N 段，不逼回前面的段，跳过的段留一句为什么。
4. 在哪做：第 2 到 8 段在目标仓的 worktree 里做，第 1、9 段哪里都行。会话不在目标仓：说明要换仓，写停靠、解绑，再到目标仓开 worktree。

工具不可用（没有 `gh`、`orca`、测试命令）时，把要做的按顺序说出来，说到停下为止，不编结果。

验收标准：第一条回复里有绑定结果、最后一条停靠记录的「下一步」、起始段，然后是那一段门口那条消息。

### 九段

| 段 | 门（等主人说行时判什么） | 产物 | 点名的步 |
|---|---|---|---|
| 1 需求分析 | 三行结论判对错 | 需求 issue，或「不是需求」（desk 仓 issue 写理由后以 `wontfix` 关） | `clarify` |
| 2 方案对齐 | 每轮判对错、确认测试接缝、收 ADR | 词汇表（`CONTEXT.md`）、ADR、spec issue | `/grill-with-docs`、`/to-spec`（主人敲） |
| 3 拆票 | 粒度与阻塞边 | 带阻塞边的票 | `/to-tickets`（主人敲；一个会话做得完就跳过，留一句） |
| 4 开工准备 | 要不要建 worktree、开哪些可选步 | worktree 加分支，基线测试过 | 建 worktree 加分支、跑一遍基线测试（desk#140 第一步，未建：按这句手做，`orca worktree create --name <名> --issue N`） |
| 5 实现 | 动手前确认接缝 | 测试与实现的 commit | `/implement`（主人敲，内含 `tdd`）；产出是一条自建 skill 时按 `skill-authoring` 走 |
| 6 验证与审查 | Critical 修不修、审查认不认 | 命令输出、审查报告、修正 commit | 跑过的命令与输出贴进对话（desk#140 第二步，未建：手做）；`code-review`；接审查意见逐条核实再改，不表演式同意（desk#140 第三步，未建：手做） |
| 7 收尾 | 合、开 PR、还是放着 | 本地 merge 或 PR | 收尾：PR 正文四节（做了什么、为什么、怎么验证的、怎么回退）；不 push、不合并、不发布，除非主人当场授权（desk#140 第四步，未建：手做） |
| 8 发布 | 灰度三档、回滚点 | 观测点与线上比对 | 多数改动跳过；要发布时 `release-observe` |
| 9 落家与交接 | 无门，随时 | 工作日志、裁决、耐用结论、交接文档 | `note`（沉淀）、`/handoff`（主人敲）、停靠记录 |

规矩：

- 门：每段结束停下等主人说行，门上判什么见表；主人说行之前不进下一段。
- 默认 skill 只能主人敲：agent 说「这是第 N 段，请敲 /名」并停下，不改用别的 skill 代替，也不开放地问主人想做什么。
- 回退：哪一段的结论被推翻，回那一段重跑，不许直接进下一段。
- 跳段：留一句为什么，写在产物里（spec、PR 正文或停靠记录）。
- 停下不做：第 1、2 段想清楚之后主人说不做，写进 issue 关掉（念头以 `wontfix` 关；机会 issue 写理由后关）。
- 未建的步：desk#140 四步建成之前按表里那句手做，不点一个调不出来的名字。

验收标准：每次停下时，能说出现在在第几段、门上等主人判什么。

### 门口那条消息

到一段的门口或起始段的入口，给主人的那条消息形状固定：先说在第几段、门上判什么，再列这段要做或已做的，最后只留一件要主人做的事。

```
这是第 N 段〈段名〉。门上判：〈门那一栏〉。
〈这段的产物或准备：一到五条〉
〈请敲 /名 ｜ 说「行」就进第 N+1 段〉
```

两个例子：

```
这是第 2 段方案对齐。门上判：每轮判对错、确认接缝、收 ADR。
已绑 issue 27，最后一条停靠记录的下一步是「主人敲 /grill-with-docs」。
请敲 /grill-with-docs。
```

```
这是第 4 段开工准备。门上判：要不要建 worktree、开哪些可选步。
- worktree：desk31-streaming-importer，分支从 main 出
- 基线：跑一遍现有测试（现在一个都没有，基线就是「没有测试」）
- 这次开的可选步：legacy-change（先录旧行为：六处脏数据处理各写一条特征化测试）、evidence-regression（改前改后导入结果逐字节比）；理由：旧代码没有测试，验收要求逐字节一致
说「行」就建 worktree、录旧行为，然后进第 5 段。
```

验收标准：消息里能数出段号、门、产物或准备、一件要主人做的事，缺一样就不是门口那条消息。

### 可选步（改旧代码时才开）

八条：`requirement-insight`（需求收口成验收判据）、`requirement-translation`（EARS 一句一例）、`architecture-design`（两候选攻防）、`system-analysis`（一个决定查一个数）、`legacy-change`（特征化测试加萌芽）、`evidence-regression`（母版逐字节比）、`integration`（列边界定顺序）、`release-observe`（放量三档加观测点）。

按缺口挑（wiki《方法论模型》表三的四个关注点）：拆——需求不清 → `requirement-insight`、`requirement-translation`；方案——两条路要比 → `architecture-design`、`system-analysis`；做——旧行为没有测试、要改的地方牵连广 → `legacy-change`、`integration`；证——改完要证明没变 → `evidence-regression`、`release-observe`。

在进第 4 段的门口列出（见上面第二个例子），和 worktree、基线一起给主人，主人说行时一并定。判据 agent 自己查（有没有测试、改动牵连几处），不问主人「这是不是旧代码」。从零新建的一个都不开，写一句「不开可选步」。

验收标准：第 4 段门口那条消息里有可选步清单和理由，或写明「不开可选步」。

### 停靠记录

时刻：每到一段的门停下等主人；主人说「先停」「我去忙了」「收工」；换仓或换 worktree 之前；开 PR、合入、发布、有关键决定或验证出结果。

写在哪：绑定 issue 下的评论（`gh issue comment`）；公开仓的事写 desk 里对应的父 issue；没绑 issue 的会话不写。`gh` 不可用就把记录贴在回复里，让主人贴。

格式固定，标题带本机时间，四栏顺序不变，「等你」只写一件需要主人定的事，没有的栏写「无」：

```
### 停靠 · YYYY-MM-DD HH:MM
做成了：<可复核的结果>
停在：<现在卡在哪一步>
下一步：<谁做什么>
等你：<需要主人定的一件事>
```

例子（第 2 段刚走完、主人说先停）：

```
### 停靠 · 2026-09-16 16:10
做成了：spec 已发成 issue #33；ADR 一条「用 restic 不用 borg」；词汇表加「增量快照」。
停在：第 2 段收口完成，第 3 段跳过（一个会话做得完）。
下一步：主人说行进第 4 段；agent 建 worktree、跑基线。
等你：说行进第 4 段。
```

验收标准：最后一条停靠记录就是现状，下一个会话读它就能接；四栏一栏不多一栏不少。

### 会话绑定

1. 一个会话或 worktree 只绑一个 issue；同一个 issue 同一时间最多一个活着的 worktree。
2. 事情要换仓：先写停靠记录，解绑旧 worktree（`orca worktree set --worktree active --issue null`），再在目标仓开新 worktree 并绑对应 issue。
3. 会话里聊出另一件事：先为它建 issue，再继续。没绑 issue 的会话一发现一次做不完，当场建 issue 并绑上。

### 结束时

1. 有后效的产出（裁决、结论、开放疑问）当场写进对应资产（去处见常驻规则「东西放哪」），不只留在对话里。
2. 挂起物（开了 PR、建了 worktree、翻成待验收）在产生那一刻登记进工作项容器或在本会话收尾，不留给事后整理。
3. 没有 issue 的外部变更（部署、本机配置、环境调整）追加工作日志；有 issue 的进展写停靠记录，不进工作日志。
4. 撞到工具链或环境的坑并绕过去：当场记一行（desk 仓「失败案例：」issue），说清撞的是什么、怎么绕过的。
5. 得出耐用结论：提议沉淀（`note`）。
6. 用一条 skill 时它让做的和实际做的对不上或别扭：建 agent-system 的反馈 issue（「反馈：<skill 名>：一句话」，`needs-triage`），不打断手上的事。

## 产出

每段的产物见表；停靠记录在绑定 issue 下。本 skill 自己不留文件。

## 出口

一条改动落地走到第 7 段的合、开 PR 或放着为止；第 8 段多数跳过；第 9 段随时。主人说「先停」也是出口：写停靠记录，停下。
