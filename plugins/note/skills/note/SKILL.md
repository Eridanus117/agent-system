# 沉淀与找回知识

第 9 阶段落家与交接点名的活动（`flow`），也随时可用。Markdown 加 git 是正文的真源（source of truth）；Rhizome 管作者契约与校验，Memex 管检索投影，目标库 `AGENTS.md` 指定的人工索引管导航与故障降级。当前实例：个人知识库在工作区的 `wiki/20-知识库/`（逻辑 source 名 `knowledge`，2026-09-13 随 desk 拆四仓独立回 wiki 仓，desk#79），工作知识库在 `logistics-kb/`。路径从工作区入口与本机源仓登记解析，正文里不写盘符与用户名；旧知识库只读参考，不作新笔记落点。

## 什么时候用

用：主人说「沉淀到知识库」「记到 KB」「/note」；对话里得出了耐用结论、关键证据或有复用价值的疑问；主人问「以前记过没」「找回那条笔记」。

不用，说一句该归谁然后停：

- 任务状态、进度、过程流水账：归站会记录或工作日志，不进知识库。
- 只对一个仓有用的局部知识：归那个仓自己的 CLAUDE.md 或 docs。
- 只是问一个事实：按查询直接答，不新建笔记。

## 步骤

1. 选库、读规则。按问题归属选目标库，读它的 `AGENTS.md`；归属、文件名、正文、合并与索引规则以它为准。只沉淀耐用结论、关键证据和有复用价值的疑问。完成判据：能各用一句说出目标库、落点目录、命名规则，都指到 `AGENTS.md` 的原文。
2. 先找回。按 [references/knowledge-loop.md](./references/knowledge-loop.md) 确认当前入口，用主人下次会怎么问的措辞检索，再读人工索引与候选正文核实；命令失败或空结果时做同义词文件检索，空结果不等于没记过。只是找回的：用正文回答、标来源，到此为止，不让主人重述已有结论。完成判据：能列出查过的措辞与命中（或「未命中」）。
3. 合并或新建。已有相近正文就更新它，没有才新建；确认本次写入所有权后才动文件，同一次改人工索引。目标库契约与 `rhizome new` 冲突（如中文文件名）时按契约直接写 Markdown，再校验。完成判据：正文与索引各一处改动，都在目标库规则允许的位置。
4. 校验与可找回。跑目标库现有校验；按 knowledge-loop.md 只编译目标源；从同一正常入口用现实问题再查一次，核对 identity 与路径并回读正文。任一环失败：报命令、退出码、错误原文、正文保留位置与文件检索结果；索引失败不回滚已保存的正文。完成判据：校验、编译、查询、回读各有一条结果；没跑到的环写「未做」，代替「已同步」「下次可找回」。
5. 收尾。只暂存本次拥有的文件，按目标仓规则提交，钩子照跑。报告：新建、更新或仅找回，库与正文位置，校验与检索结果，未沉淀的开放疑问；部署或索引仍受阻的分开说。完成判据：报告里每条声称能指到一条命令与结果（`verify-evidence`）。

## 产出

目标库里一篇新建或更新的 Markdown、人工索引的一行、一次提交；或一次带来源的找回回答。

## 出口

到提交与回读为止；索引服务、向量同步、计费模型不在这里启动。
