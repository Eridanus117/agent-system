# 方案：PR 门禁归位（CI 结构）

2026-09-03，负责人对仓库审计的 C 组第 1、3 项要求出方案。两项是同一个决定，合写。本篇是 vibeCoding 的「方案」步骤试跑：形状取 workCoding 骨架第二段的五节（现状 / 怎么改 / 怎么验 / 怎么回退 / 怎么接入），按小事缩短。负责人裁定前不改任何工作流。

## 要裁什么

一句话：**三个 Bun 包（control-plane、harness-engine、sk）的 PR 门禁放在哪条工作流里。**

## 现状（事实）

| 包 | PR 上谁在跑 typecheck + test | 推 main 时 | 平台 |
|---|---|---|---|
| control-plane | `control-plane-checks.yml`（ubuntu + windows）**和** `release-configs.yml` 的 validate-release 作业 | 只有 checks | 3 个作业做同一件事 |
| harness-engine | `harness-engine-checks.yml`（#39 新加，ubuntu + windows） | 跑 | 正常 |
| sk | 只有 `release-sk.yml` 的 validate-release 作业 | **不跑** | 只 ubuntu；门禁藏在名叫 Release 的工作流里 |

补充事实：两条 release 工作流的 release 作业在打 tag 时会自己再跑一遍 install、tsc、test，所以 validate-release 作业的唯一用途就是当 PR 门禁。分支保护现要求 5 个必需检查（名字含 validate-release），改工作流名字必须同步改分支保护，否则 PR 会永远等一个不会到来的检查（#39 合并时已实际碰到「5 of 5 required status checks are expected」）。

## 备选（业界做法）

| 方案 | 做法 | 适用 | 代价 |
|---|---|---|---|
| A 一包一条 checks 工作流 | 给 sk 也加 `sk-checks.yml`；两条 release 工作流去掉 `pull_request` 触发与 validate-release 作业 | 包少、想按包看红绿 | 三份几乎相同的 YAML，改一处要改三处（本次 #39 就是复制粘贴出来的） |
| **B 一条工作区级矩阵工作流（推荐）** | 新建 `packages-checks.yml`：矩阵 package × os（3 × 2 = 6 个作业），仓库根 `bun install --frozen-lockfile` 一次，各作业进包目录跑 typecheck + test；删 `control-plane-checks.yml`、`harness-engine-checks.yml`；两条 release 工作流去掉 `pull_request` 触发与 validate-release 作业 | Bun / npm workspace 单仓的常规做法 | 分支保护的必需检查要从 5 个换成 6 个矩阵作业名；一个包红整条工作流名显示红（矩阵作业名可区分，`fail-fast: false`） |
| C 以 release 工作流的 validate 作业为唯一门禁 | 删两条 checks 工作流；harness-engine 没有 release 工作流，要另加一条 | 想少文件 | 门禁藏在名叫 Release 的工作流里，可读性最差；只 ubuntu；harness-engine 仍要特例 |

不选 A：重复已经在产生错误（三份 YAML 各自漂移正是本次审计发现的问题）。不选 C：可读性与平台覆盖都退步。

## 怎么改（B 的具体内容）

1. 新建 `.github/workflows/packages-checks.yml`：`on: pull_request / push(main)`；`strategy.matrix.package: [control-plane, harness-engine, sk]`，`os: [ubuntu-latest, windows-latest]`，`fail-fast: false`；`oven-sh/setup-bun@v2` 钉 `1.3.14`；仓库根 `bun install --frozen-lockfile`；`working-directory: packages/${{ matrix.package }}` 跑 `bunx tsc --noEmit` 与 `bun test`（harness-engine 的脚本是 `bun test tests`，用 `bun run test` 统一走各包 package.json 的 `test` 脚本即可）。
2. `release-configs.yml`、`release-sk.yml`：删 `on.pull_request` 与 validate-release 作业；release 作业本身不动。
3. 删 `control-plane-checks.yml`、`harness-engine-checks.yml`。
4. 分支保护必需检查：改为 6 个矩阵作业名（`test (control-plane, ubuntu-latest)` 等）加原有的 `checks`、`conformance`、`validate`。

不做：依赖缓存（C 组第 4 项，另议）；`repository-checks.yml` 不动。

## 怎么验

- 方案 PR 上 6 个矩阵作业全绿，且 PR 页面「必需检查」没有一直 expected 的项。
- 合并后随便开一个只改 `packages/sk` 的 PR，确认 sk 的 typecheck 与 test 在 PR 上跑，且推 main 时也跑。

## 怎么回退

revert 该 PR 即回到现状；分支保护的必需检查列表要手工改回（GitHub 设置，不在 git 里，这是本方案唯一不能靠 revert 回退的部分）。

## 怎么接入（顺序，每步可单独退）

1. 先加新工作流，旧的不删，跑一次看 6 个作业绿。
2. 改分支保护：把 6 个新作业设为必需，旧的 validate-release 与 control-plane/harness-engine 的 `test (…)` 取消必需。
3. 再删旧工作流与 release 工作流的 PR 触发。

第 2 步是 GitHub 仓库设置，需要负责人在网页操作或授权 agent 用 `gh api` 改。
