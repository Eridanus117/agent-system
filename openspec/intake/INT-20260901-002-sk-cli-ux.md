# Intake

## 原始问题

测试成功，看看优化一下这个cli 的体验

## Triage

范围：`packages/sk` 的 CLI 交互体验（错误反馈、输出可读性、检索效率），不改数据模型与派生文件格式。
影响：日常高频命令是 list/show/add/rm/run；当前库存 63 个技能，检索与错误反馈的摩擦每天都会碰到。
判断：范围待负责人在门1圈定候选项后即清晰，预计 light-change 快车道。

## Evidence

### 已知事实

- 2026-09-01 实机走查全部命令（dev 构建，真实库根 63 技能 / 2 profile）。

### 未知与假设

- 假设负责人日常直接手敲 sk（而非只经 agent 调用），错误反馈与检索效率是主要体验面。
- 配色/交互式选择等重型体验改造假设为不需要（反过度工程）。

### 证据

- 摩擦A 打错命令名：`sk shwo all` 静默打印帮助且退出码 0，无「不认识的命令」提示；脚本里更会误判成功。
- 摩擦B 库存不可检索：`sk list` 固定输出全部 63 行，无模式过滤；找单个技能要翻全屏或外接 grep。
- 摩擦C 误导性报错：`sk rm <不存在的profile> <模式>` 报「模式未匹配任何技能」，实际是 profile 不存在（cmdRm 未先查 profile 目录）。
- 摩擦D 描述截断无标记：list/show 的描述列 60 字符硬截断（按 code unit），中文描述断得突兀且无省略号，看不出被截断。

### 使用建模（2026-09-01 第二轮，负责人要求先建模「人为什么用、会怎么用」）

依据：desk 提案「2026-08-26-Skills管理工具」的需求对齐（R1 库存认知 / R2 预设 profile 五六到十几种 / R4 session 隔离）与验收标准（任一目录一条短命令按 profile 启动、同目录多 session 互不影响）。

- **人想解决的问题（三层）**：表层是控制 skills 加载；中层是 session 上下文预算——技能描述常驻 system prompt，无关技能是噪音与误触发源；底层是**情境切换**——负责人在写作/开发/研究/流程治理等情境间切换，希望「一个情境名唤起一整套工作台」。profile 的本质是**给情境命名**。
- **双用户**：①负责人手敲——要可发现、命令短、报错对症；②agent 代驾（门文化下大量操作由 agent 执行）——要退出码正确、输出可解析、无交互阻塞。摩擦A 对两者都是伤害。
- **时刻与频率地图**：启动（高频，`run`）＞ 观察（中频，`list/show`）＞ 策展（低频，`new/add/rm`）＞ 维护（稀有，`restore/sync`）。体验投入应按此排序；已修的 show 与候选 A–D 主要服务观察与策展层，高频 `run` 路径尚未建模（每次要敲 CLI 名，情境→CLI 是否有稳定绑定待负责人回答）。
- **现状与愿景差**：R2 设想五六到十几个情境 profile，现实只有 all（全量）与 general（4 个技能）——工具尚未进入真实使用期；「体验优化」的最大杠杆可能不是打磨命令，而是让策展轻到情境 profile 库真的建起来。
- **明确不做（反过度工程）**：配色/TUI/交互式选择；「session 实际用了哪些技能」的反馈回路（无真实消费方，记为开放疑问）；与 agent-system Role 激活体系的合流（profile≈Role 的技能维度，长期问题，另立事项）。

### 第三轮定性（2026-09-01，负责人质询后修正）

- 负责人质疑「profile 过少」的归因：不是策展摩擦，怀疑是「没有找到优化工作流的好方式」。
- 库存证据支持该怀疑：63 个技能中 49 个是 bmad 整套框架（自带用法，不参与日常组合），自建 14 个几乎全是元技能（盘问、反思、知识维护）；「干某类具体活」的领域技能为零。
- 修正后的因果链：各条工作流尚未沉淀成技能 → 无货可组合 → profile 无需求 → sk 使用薄。CLI 体验不是瓶颈，工具建在了需求前面。
- 推论：正确顺序是「跑工作流 → 把反复交代 agent 的话沉淀成 SKILL.md → 技能攒够 → profile 自然出现」，而非先设计 profile 体系。库内 skill-appraisal / skill-maintenance 即为沉淀步骤准备的既有工具。
- 处置走向：本事项（CLI 体验打磨）建议缓；sk 本体按门C留用（薄启动器已达验收标准）；真正的下一个话头是「挑哪条工作流先沉淀」，属新事项，由负责人择时发起。

### 第四轮（2026-09-01，负责人裁定 bmad 退库）

- 负责人原话「把bmad 去掉，我不用 bmad」，即 matters.json 所要求的产品政策级确认。已执行：vendor/bmad（49 Skill、243 文件）整组退库；all profile 63→14；skill_registry 登记面（bmad 组条目、E5 重叠判定、生成器散文、scanRoots/groupRules）、.gitignore、skill-asset-checks 工作流、sk 文档示例同步清理。skill-registry --check、sk 与 plugins 测试全绿。
- 遗留跟进：① adaptive-problem-solving 0.2.13 的「与装配内其他 Skill 的分界」表与失效条款仍引用已退库的 bmad-*，需一次 skill-maintenance 过手（含版本递进）；② 仓库 AGENTS.md 仍以 _bmad-output 为产品政策权威、_bmad/ 安装态仍在库——「不用 bmad」是否延伸到重锚产品政策权威，属治理级开放疑问，待负责人裁。
- 同轮负责人要求更上层建模（用 BMAD 在做什么/解决什么问题/我们在什么流程中），建模结论见对话交付与 desk 提案使用期记录。

## Options

### 候选处置

1. **建（第一轮候选）**：A 未知命令报错并退出码 1（显式 `sk`/`--help` 仍为 0）；B `sk list [模式...]` 复用既有 glob/@组名匹配做过滤；C `sk rm` 先查 profile 存在性、对症报错；D 截断处补省略号。
2. **建（建模后新增候选，待负责人圈选）**：E `run` 高频路径缩短——profile 记默认 CLI（如 `sk run 写作` 即够）或更短形态，取决于负责人「情境→CLI」的真实绑定习惯；F `sk which <技能>` 反查哪些 profile 含某技能（服务库演化时刻：新技能进库后决定进哪些 profile）。
3. 不建/缓：现状可用，先真实策展一轮情境 profile，让摩擦自己浮现。
