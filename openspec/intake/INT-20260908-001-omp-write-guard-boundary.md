# Intake：OMP write guard 的写入边界该由什么判定、在哪一层执行

本记录是**未收敛事项**，按 AGENTS.md「未收敛的事项停留在 intake 的已知/未知层」保存。
推荐不是授权；负责人未逐项裁决前不改 guard 源码、不改部署、不新增许可机制。
agent 的推断一律标注为「假设」。

## 决定

**这轮要决定**：write guard 判定写入是否放行时，判定对象是什么（目标路径 / 会话 cwd / 会话租约），
以及这个边界在哪一层执行（工具参数检查 / 操作系统可写集 / 明确放弃并声明）。

**这轮不决定**：具体实现细节、是否立即实施、沙箱的技术选型、许可清单的维护者。

**谁受影响**：所有经 control-plane 启动的 OMP 会话；负责人本人的日常仓外配置维护当前被此边界阻断。

## 基线

### 已确认事实

来源：`packages/control-plane/src/adapters/omp/extensions/agent-status-extension.ts`（940037c 版本，402 行）。

- `evaluateWriteGuard()`：若任一目标上下文为 `null` 或 `branch === null` 或 `!isLinkedWorktree`，整次拒绝；随后再拒受保护分支（main/master/trunk/origin 默认分支）。
- `targetDirectories()`（191-200 行）：**bash 直接返回 `[cwd]`**，不解析命令里的真实写入目标；结构化工具取 `input.path` / `input.paths`，做 `path.resolve` + `path.dirname` + 最近存在祖先，**没有 realpath**。
- `isReadOnlyShellSegment()`（148 行）：正则白名单，**`sed` 在白名单内**，而 `sed -i` 是原地写。
- 合同测试 `packages/control-plane/tests/contracts/omp-write-guard.test.ts`（149 行，11 项）。第 54 行测试名为
  "checks the repository owning a direct target path instead of trusting session cwd"——**该性质只对结构化工具成立**。
  涉及 bash 的用例（113 行）用 `isLinkedWorktree = false`，因此**从未覆盖「linked worktree + 任务分支 + 写命令 + 任意目标」这一实际工作态**。
- PR #50 标题「增加 OMP 受保护分支写入守卫」；PR #52 标题「要求所有 OMP 写入使用仓库 linked worktree」。
- 部署态 `~/.agent-system-state/control-plane/extensions/agent-status-extension.ts` 与源码逻辑一致（402 行 / 13524 字节，仅空行位置差异）。
- OMP `~/.omp/agent/config.yml`：`tools.approvalMode: yolo`——**宿主审批门当前是关的**。
- 实际拒绝案例：对 `~/.config/rhizome/sources.toml` 的结构化 edit 被拒，理由 `repo=unknown`。

### 实测：同一目标，四条路径四种结果

2026-09-08 直接 import 当前源码的 `evaluateWriteGuard`，注入 `RepoContextReader`
（cwd 在 linked worktree 的任务分支上；目标目录不属于任何仓库故返回 `null`）。
**纯内存判定，未发生任何真实写入。**

| 路径 | 守卫判定只读 | 结果 |
| --- | --- | --- |
| 结构化 `edit` 写 `~/.config/rhizome/sources.toml` | 否 | **拒绝** |
| `bash cp /tmp/x <同一目标>` | 否 | **放行** |
| `bash sed -i 's/a/b/' <同一目标>` | **是** | **放行** |
| `bash python -c "open(<同一目标>,'w')"` | 否 | **放行** |

### 该事实的含义

守卫**拦住了可审计的那条路，放行了三条不可审计的路**，目标完全相同。
因此 PR #52 标题所声明的性质（所有 OMP 写入都在 linked worktree 内）**当前并不成立**；
它只对参数里完整写出目标的结构化工具成立。

## 候选

### 候选 A：分层诚实化——guard 只管仓库状态，不假装做围栏

- **判定对象**：每个**能完整确定的**写入目标的 realpath。
- **结构化工具**：解析 realpath。落在仓内 → 照旧适用「linked worktree + 非受保护分支」规则；
  **确证仓外 → 放行**（不是 guard 的职责）；无法解析 → 仍拒绝。
- **bash**：**放弃「用 cwd 冒充目标」的虚构**。改为识别**会改动 git 状态的命令**
  （commit/checkout/reset/rebase/merge/push/clean/stash 等），按 cwd 所属仓库判定；
  其余 bash 不属于本 guard 职责，放行。
- **shell 分类器默认方向反转**：今天是「认不出就当写入、按 cwd 判」，改为「像 git 且认不出就当会改 git 状态」。
  误判代价从「放行一次真实写入」变成「多拦一条 git 只读命令」。
- **`sed` 从只读白名单移除**（`sed -i` 是写）。
- **显式声明**：本 guard 不是围栏，是防误伤的护栏。围栏是另一个尚未解决的议题。
- 迁移影响：合同测试需改写——第 54 行那条测试的性质要么扩到 bash，要么改名以反映其实际范围。

### 候选 B：真沙箱——把边界下沉到操作系统可写集

- 会话启动时声明可写根（自己的 linked worktree + 临时目录 + 显式授予的配置路径），其余只读。
- 由操作系统而非命令解析强制执行，**bash 自动被覆盖，不需要任何 shell 解析**。
- 迁移影响：需要处理大量基础设施写入（npm/bun 缓存、`%APPDATA%`、mise shims、git 全局配置）。

### 候选 C：保留默认拒绝，为受管配置加显式许可（交接文档 2026-09-07 原推荐）

- 结构化工具维持全域默认拒绝；新增一份可信来源维护的受管配置许可清单；
  目标确证仓外且在清单内才交回宿主权限。
- bash 一侧**完全不动**。

## 攻防

### 候选 A

- **支持**：与实测事实一致——它不减少任何**实际生效**的保护，只是把**声称**的保护缩到与实际相符。
  按 openspec `config.yaml` 原有的 `technical-current` 规则「区分声明态、配置态和实际生效态」，
  当前正是声明态与生效态不符，A 直接消除该不符。同时顺带解决负责人日常仓外配置维护被阻断的问题，
  且是作为正确分层的**推论**，不是开特例。改动集中在一个文件加其合同测试，可逆。
- **反对**：`approvalMode: yolo` 意味着「交回宿主原权限」**当前等于没有门**。
  A 会让结构化工具写任意仓外文件时不再有任何拦截。
- **对该反对的回应**：这个风险今天已经存在且更严重——同一目标经 bash 三条路径全部畅通，
  且 bash 路径不产生可复核的结构化记录。A 把风险从「不可见地存在」变成「可见地存在」。
  但这不等于风险消失，**若负责人在意这条，正确动作是打开 OMP 审批门或做 B，而不是保留 A 之前的形状**。
- **最大风险**：负责人若原本要的就是围栏，A 会把一个坏掉的围栏正式降级为护栏，
  而围栏本身没人去建，议题就此沉底。
- **可逆性**：高。单文件加测试，可回退。

### 候选 B

- **支持**：唯一能真正成立的围栏。不依赖 shell 解析，因此不存在「解析器永远追不上命令写法」的军备竞赛。
- **反对**：Windows 上实现代价未知且很可能很高（无 Linux 的 namespace/bind-mount 等价物，
  可能需要受限令牌加 DACL、文件系统筛选器或容器）。基础设施写入的允许清单本身是个持续维护负担。
- **最大风险**：做成一个半成品沙箱——挡住了正常工作却挡不住真正的越界，比现状更差。
- **可逆性**：低。是一项工程，不是一次修改。
- **前置**：需要一次 `system-analysis` 才能给出代价数字。**本记录不编造该数字。**

### 候选 C

- **支持**：改动最小，不触碰现行合同的形状，不需要负责人重新裁边界的语义。
- **反对**：**建在沙地上**。它在一个已被实测证明有洞的基础上加一层许可机制——
  bash 侧的假阴性一条不少。结果是既增加了信任面与维护负担（谁维护清单、清单存哪、
  怎么保证被拦的 agent 不能自填），又没有换来任何真实的保护提升。
- **最大风险**：把「已经有一套许可机制」当成「边界已经收口」，进一步固化声明态与生效态的不符。
- **可逆性**：中。但引入的许可机制本身会长出依赖。

## 推荐（暂定，非授权）

**推荐候选 A**，并把候选 B 作为**独立的后续决定**、需要先做一次 `system-analysis` 才能谈。
**显式否决候选 C**：理由是它在已被实测证伪的基础上加机制。

推荐 A 的核心理由不是「A 更方便」，而是：
**现行设计把两个不同的问题压成了一个判据**——
「这次写入会不会破坏 git 仓库状态」（可由目标路径回答）
与「这次写入到底该不该被允许」（是授权问题，路径启发式回答不了）。
用路径启发式回答授权问题，必然同时产生假阳性（正当的仓外配置维护被拦）
和假阴性（bash 到任意目标畅通），且**假阴性无法在这一层根治**：
静态判定任意 shell 命令的写入目标在一般情况下不可判定
（变量、命令替换、管道进 tee、脚本、构建工具）。
继续在这一层堆 shell 解析器是把工程投在一个不可能收敛的方向上。

**会推翻本推荐的证据**：
若负责人确认 PR #52 的原意就是围栏且围栏是硬需求，则 A 不足，应直接进 B 的可行性分析；
若查明 OMP 本身已提供可用的沙箱或权限设施，B 的代价评估将大幅改变，B 可能直接优于 A。

# 需求修正（2026-09-08，负责人）：本节取代上文的「决定」与「推荐」

## 负责人原话

> 其实是因为我发现 agent 很喜欢在主干分支上写，我觉得这样不行。

同时负责人对「PR #52 当初要围栏还是要可复核」答「当时没分得这么清楚」。

**因此上文的整个取舍框架是错的**：围栏与仓外管控都不是需求，二者都是手段过头的附带结果。
真需求是**仓库状态保护**这一件事，而且落点更具体——**不要在主干分支上写**。

## 实测二：现行 guard 在这个真需求上直接不成立

2026-09-08 第二次探测。这次**不注入**，使用源码自带的 `defaultRepoContextReader`，
读真实磁盘上的仓库状态。cwd = `C:/Workspace/worktrees/agent-system/guard-boundary-design`
（linked worktree，任务分支）；目标 = `C:/Workspace/desk/AGENTS.md`（主检出，main 分支）。
**纯判定，未发生真实写入。**

| 路径 | 结果 |
| --- | --- |
| 结构化 `write` 直写主检出 main 上的文件 | **拒绝** |
| `bash echo x >> <同一文件>` | **放行** |
| `bash cp /tmp/x <同一文件>` | **放行** |
| `bash cd C:/Workspace/desk && git commit -am x` | **放行** |

**结论：agent 今天可以从一个 linked worktree 出发，用 bash 直接改写主检出 main 上的文件，
并在 main 上创建提交。这正是负责人描述的那个行为，guard 完全没有拦住它。**

机理同前：`targetDirectories()` 对 bash 只返回 `[cwd]`。
附带确认 `cd` 在只读白名单内，故 `cd <主检出> && git commit` 这种形状连分段检查都过得去。

## 候选修正

**上文候选 A 在真需求下不够。** A 的 bash 一侧只识别「会改动 git 状态的命令」，
而 `echo >>`、`cp`、`sed -i` 这类普通文件写入不是 git 命令，却正是要拦的行为。

### 候选 A′：guard 只管仓库状态，且 bash 必须按真实目标判定

- 结构化工具：解析 realpath；仓内按分支与 worktree 规则；确证仓外放行；解析不出拒绝。
- bash：**不能只看 cwd**。尽力提取命令的写入目标——重定向 `>` / `>>`、`cp` / `mv` / `rm` / `tee` /
  `touch` / `mkdir` / `sed -i` 的目标参数、git 变更子命令、以及 **`cd` 对有效 cwd 的改变**；
  按提取出的目标判定。提不出目标的命令放行。
- **关键论证**：这是启发式，对**规避**无效，但需求是防**粗心**——
  负责人描述的是 agent 的习惯性行为，不是对抗行为。因此启发式在这里是**充分**的，不是妥协。
- 代价：shell 解析器会持续长大；`cd` 语义必须处理，否则 `cd <主检出> && ...` 直接绕过。
- **假设（未经确认）**：agent 非对抗。若将来要防对抗，A′ 不够，需候选 D。

### 候选 D：反向沙箱——只把受保护检出对 agent 进程设为只读

- 不做通用可写集。只把**可枚举的受保护检出**（`git worktree list` 的主 worktree，
  或处于受保护分支的检出）对 agent 进程设为不可写。
- 由操作系统强制，bash 与任意子进程自动覆盖，**零 shell 解析**。
- 相对上文候选 B 的关键改进：**拒绝一个小的可枚举集合**，而不是**允许一个大的开放集合**，
  因此 B 最难的那个「基础设施写入允许清单」问题不存在。
- 未知：Windows 实现路径（受限令牌加 deny ACE？以不同用户运行？）与代价。仍需 `system-analysis`，
  但问题规模比 B 小一个量级。**本记录不编造该代价。**

## 与现行工作区规则的正面冲突（必须由负责人裁）

**`C:/Workspace/CLAUDE.md:32` 明确要求 agent 直接向 desk main 提交并推送**：

> 写入和读取前在 desk 仓执行 `git pull --rebase origin main`；写入后只提交 `70-工作日志/` 的变更并 `git push origin main`

desk `AGENTS.md` 的写入白名单五类（提案门状态、收件箱、工作区地图、`80-agent配置/`、`60-迁移/`）
同样都是直接写 desk main。本会话本身就多次这样做。

因此「agent 不该在主干分支上写」**不能按字面全域实施**，否则会直接违反现行工作区规则。
需求必须限定范围，而范围只有负责人能定。可能的切法（供参考，非推荐）：
按仓分（源码仓管，记录仓不管）；按内容分（实质改动管，追加式记录不管）；
或者反过来改 desk 规则让日志也走 worktree（与「日志是工作完成的一部分、当场写」的即时性冲突）。
