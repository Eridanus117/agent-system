# 改造方案

## 目标

将当前以 OMP/Claude `ClientAdapter` 为中心的控制面收敛为 Agent-neutral 合同，并通过 Orca 调度边界支持已核实 provider 的计划、派发和观察证据链。保留六边形模块化单体：domain 保持纯净，application 是状态变更入口，Orca、SQLite、Agent process 和文件系统通过 ports/adapters 接入。

本 change 的第一条切片是 Agent Registry、Agent capability snapshot、AgentScheduleIntent、DispatchOperation、Orca scheduler/dispatch adapter、SQLite 事实和 OMP/Claude 术语迁移。Codex、Pi、Grok、Hermes 及其他 provider 的 native assembly 仍需独立 provider 计划和宿主证据。

## 稳定合同

### Agent Registry

```text
AgentId
AgentDescriptor {
  id,
  displayName,
  provider,
  sourceEvidence,
  supportLevel,
  version,
  capabilities
}
CapabilitySnapshot {
  probeId,
  observedAt,
  version,
  launch,
  schedule,
  worktree,
  sessionPolicy,
  contentAssembly,
  evidence
}
```

`supportLevel` 使用封闭集合：`supported | degraded | unsupported | unknown`。可见、宿主安装、probe、真实启动和实际生效分开表达。没有 provider inventory 证据时返回 `unknown`，不能从 Orca 接受 provider 字符串推出支持。

### AgentAdapter

当前 `ClientAdapter` 的概念迁移为：

```text
probe(revision?)
prepare(operation, revision)
start(operation, prepared)
observe(operation, started)
abort(operation, prepared, started?)
```

每个 adapter 可保留自己的 argv、文件、环境和权限语义，但统一返回 `manifestHash`、launch context、process reference、observation outcome 以及 reason/evidence reference。OMP 继续传递 Skill 名称；Claude 继续按 invocation 目录物化 instructions、Skills 和 MCP，不做配置或 Session 等价化。

### 调度与派发

```text
AgentScheduleIntent {
  scheduleId,
  agentId,
  revisionId,
  trigger,
  target,
  sessionPolicy,
  precheckRef,
  sourceContextRef,
  requestedBy,
  createdAt
}

OrcaAutomationReceipt {
  automationId,
  provider,
  target,
  trigger,
  createdAt,
  sourceEvidence
}
```

`trigger` 支持 preset（`hourly`、`daily`、`weekdays`、`weekly`）、5-field cron 或 RRULE；`target` 支持 repo、workspace、project/host 和 runtime；`sessionPolicy` 支持 `fresh`/`reuse`。调度意图中的 `precheckRef`、`sourceContextRef` 是受控引用，不保存动态任务原文或凭据。

每次运行还要产生 `DispatchOperation`，至少关联 `operationId`、`scheduleId`、`agentId`、`revisionId`、target、manifestHash、phase 和 automationId。automation 创建成功仅进入 `dispatched`；到点 precheck 失败进入 `skipped`；只有独立 Agent 启动和 observation 证据才能产生后续终态。

## Orca 映射与外部边界

Orca 版本匹配证据为 runtime `1.4.192`，已知 ID 为 `claude`、`codex`、`omp`、`pi`、`grok`，并允许 generic installed TUI providers；调度入口固定为 `orca automations create --provider <agent>`。实现应通过注入的 `OrcaCommandPort` 传递 argv 数组，不执行 shell 字符串，只解析 `--json` 输出。

Orca adapter 负责把调度意图映射到 `orca automations create`，并回传 automation receipt；取消和 reconcile 必须再次通过端口并验证 JSON/ID。`orca worktree create --agent <id>`、计时器、RRULE、worktree、terminal、host 和 Agent 进程生命周期由 Orca 拥有，Agent System 不在 domain/application 中重新实现。

`orca agent-context --json` 是机器可读合同证据，但当前没有单独的“列出全部已安装 Agent provider”命令。Hermes 未出现在当前 CLI 指南已知 ID 中，保持 `unknown`，不创建 Hermes adapter。

## 不变量、失败关闭与隐私边界

- Agent、revision、schedule、operation、target 和 manifest hash 必须可关联；任一关联不匹配保持 `unknown`/`incomplete`。
- provider 未发现、版本/能力未知、Role/revision 无法物化、Orca 创建失败、precheck 非零、目标不可用或观察不足时 fail closed。
- 状态和证据区分 planned、dispatched、observing、succeeded、degraded、failed、skipped、unknown；退出码为零不能直接推导 `verified`。
- SQLite 是产品事实唯一持久权威；manifest、receipt、automation ID 和 launch context 只按 allowlist 保存。
- 动态任务原文、prompt、凭据、transcript 和 `.orca/` 运行状态不进入稳定 revision、schedule、receipt、日志或投影。
- 不宣称跨系统事务原子性。外部副作用和 SQLite 事务分别记录，失败/取消/超时/未知结果必须有明确收口。

## 验证、权威与回滚边界

- 本 Task 只验证 OpenSpec 结构：`npx openspec doctor` 与 `npx openspec validate orca-agent-scheduling --strict`。
- 实现阶段另行运行合同测试、定向集成测试、dry-run 和 provider/宿主 smoke；没有实际宿主证据不得把 provider 标记完整 `supported`。
- 本 change 先保持 `skip_specs: true`，不修改 `openspec/specs/`；只有实现证据存在并经过生命周期验收后才考虑同步长期规范。
- 不创建真实 Orca automation，不修改 `.orca/`；dry-run 是默认路径。发生输入、映射或关联失败时只保留失败证据并拒绝写成功事实。
- 回滚以不产生外部 automation 副作用为前提：撤销本 change 文件或未落地的应用事实，不删除客户端拥有的配置、Session 或 transcript。
