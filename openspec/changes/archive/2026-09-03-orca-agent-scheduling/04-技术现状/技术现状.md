## OMP 当前实现

`OmpClientAdapter` 位于 `packages/control-plane/src/adapters/clients/client-adapters.ts`：

- `clientId` 为 `omp`，binary 为 `omp`。
- `probe` 先读取 `omp --version`，再读取 `omp --help`；若 revision 含 Skill，则要求 `--skills`，否则要求 `--no-skills`。
- `prepare` 在状态根的 `launch-context/` 写入含 version、operationId、revisionId、configName、client 的调用上下文，并返回其路径及默认扩展路径。
- `buildArgv` 调用 `buildOmpArgv`，将 revision、context path、extension path 和转发参数交给 OMP；这证明当前 OMP native 参数边界，不能推断 Orca 调度已经实现。
- `start` 使用 `Bun.spawn` 数组参数启动，不经过 shell；`observe` 按退出码/信号产生观察结果；cleanup 删除调用上下文文件。

## Claude 当前实现

`ClaudeClientAdapter` 位于同一 adapter 文件，并使用 `adapters/clients/claude/content-materializer.ts`：

- `clientId` 为 `claude-code`，binary 为 `claude`。
- `probe` 依据 revision 检查 `--append-system-prompt`、`--plugin-dir`、`--mcp-config` 和 `--strict-mcp-config` 是否出现在 help 中。
- `prepare` 创建临时 invocation 目录，通过 `FsClaudeContentMaterializer` 解析 instructions、skills、MCP；任一物化失败即抛错并清理，不用空内容代替。
- `buildArgv` 将 instructions 作为 `--append-system-prompt`，Skills 作为一次 `--plugin-dir`，MCP 作为 `--mcp-config` 与 `--strict-mcp-config`。
- `start` 使用 invocation 目录作为 cwd 和 `CLAUDE_CONFIG_DIR`，通过 `Bun.spawn` 数组参数启动；`observe` 等待进程终态，并在 finally 中清理 invocation 目录。
- 这些代码证明调用期物化和清理路径存在，不证明真实 Claude interactive Session 或任务行为已验收。

## Orca 外部合同证据

负责人审阅设计记录的版本匹配 CLI 读取结果为：

- runtime ready，版本 `1.4.192`；
- 已知 Agent ID：`claude`、`codex`、`omp`、`pi`、`grok`；同时允许 generic installed TUI providers；
- `orca worktree create --agent <id>` 是工作树首个终端启动入口；
- `orca automations create --provider <agent>` 是调度入口；
- 支持 `hourly`、`daily`、`weekdays`、`weekly`、5-field cron、RRULE，以及 repo、workspace、project、project host、远端 runtime 目标和 precheck/fresh-session/reuse-session/timezone/missed-run grace 选项；
- `orca agent-context --json` 提供机器可读合同，但当前没有单独的“列出全部已安装 Agent provider”命令；
- `Hermes` 未出现在当前 CLI 指南已知 ID 中，保持 `unknown`。

以上只说明 Orca CLI 合同和已读证据，不说明所有 provider 已安装、可启动或已通过 Agent System 观察验收。

## 当前缺失的技术边界

当前 `packages/control-plane/src` 没有 Agent Registry、AgentScheduleIntent、DispatchOperation、Orca command/scheduler/dispatch adapter 或 schedule/dispatch SQLite repository 的正式实现。下一阶段应通过 ports/adapters 增加这些边界，并保留下列不变量：

1. `AgentId`、revisionId、operationId、target 和 manifestHash 贯穿 schedule、dispatch receipt 与 observation。
2. trigger 只表达 preset、5-field cron 或 RRULE；target 表达 repo、workspace、project/host 或 runtime；Session policy 只表达 fresh/reuse。
3. Orca automation 创建成功只进入 `dispatched`，不进入 `succeeded`；precheck 失败进入 `skipped`。
4. 只解析 `--json` 输出；非零退出、非法 JSON、缺少 automation ID 或无法关联的回执进入类型化失败/unknown，不产生伪造成功事实。
5. domain 保持纯净，SQLite 是产品事实权威；动态任务原文、prompt、凭据和 transcript 不进入持久记录。
