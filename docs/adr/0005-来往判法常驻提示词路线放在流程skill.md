# 来往判法常驻提示词，路线放在流程 skill 里、判为改动落地才读

## 背景与问题（Context and Problem Statement）

- 2026-09-14 负责人定（desk#142）：私人机上只有一套工作模式，由一个流程 skill 承载；它是所有 skill 的唯一入口，其他 skill 只在它点名或主人敲 `/名` 时才用；路线真源从共用规则挪到流程 skill（desk#141 作废）。
- 现状：九段路线、每段点名谁、「怎么开始、怎么结束」都写在 agent-config 的共用规则里，由 `deploy.ts` 编译进三个客户端的上下文文件（CLAUDE.md／AGENTS.md），每场每轮常驻，约占 120 行里的 45 行。
- 主人与 agent 的来往只有三种：要答案、小改动、改动落地（定义见 `plugins/CONTEXT.md`）。只有第三种会用到段；前两种会话背着九段的规程没有用处。
- 2026-09-16 方案对齐时负责人问：如果流程 skill 每场必读，它和提示词有什么区别？

请负责人定的一件事：路线放哪——全放 skill、全放提示词，还是分开；分开的话线画在哪。

## 决策驱动因素（Decision Drivers）

- 一个真源：同一句话只在一处（desk#141 的诉求）。
- 改得勤的东西要便宜改、能测、能回退：负责人定「直接装、用中改」；#140 四步落地、`workcoding` 退役、用中记的反馈都会改路线。
- 第一句回复之前就要知道的东西不能靠 agent 自己去读，必须常驻。
- 提示词越长，每条被遵守的概率越低；前两种会话不该背第三种的规程。
- 三个客户端行为一致。

## 考虑过的方案（Considered Options）

| 方案 | 做法 | 适用场景 | 代价 |
|---|---|---|---|
| A 全进 skill | 共用规则只留一句「开场一律先读流程 skill」；分拣与路线都在 skill 里 | 三个客户端都能可靠地在第一轮读 skill | 每场都要读，等于提示词换了个装法；每场都多一个漏读点；前两种会话白背 100 行 |
| B 全进提示词 | 不建流程 skill，路线留在共用规则 | 路线基本定型、不再改 | 改一次要 PR 加 `deploy.ts sync`；没有对照组 eval；三个客户端的提示词各多约 60 行常驻 |
| C 分开 | 共用规则留十来行：三种来往怎么分、开场那一句与等不等、说话的规矩，加一句「判为改动落地就读流程 skill」；流程 skill 装九段的顺序、门、回退、跳段、从任一段进、每段点名的步、可选步、会话绑定、停靠与挂起物 | 既有定下来基本不动的规矩，又有会反复改的规程 | 流程分在两个文件；Codex 与 OMP 在第三种会话里读不读 skill 要上线时验证 |

## 决定结果（Decision Outcome）

选 **C**。分界线不是「提示词还是 skill」，是「第一句回复之前就得知道的」和「进了段才需要的」：前者是主人与 agent 的说话规矩，定下来基本不动，该常驻；后者是会被反复改的规程，放在便宜、能测、能回退的地方。

不选 A：每场必读就是提示词，还多一个失败点。不选 B：路线要改得勤，PR 加 sync 太重，且没有 eval 可跑。

接入顺序（每步可单独退）：

1. 本仓建 `plugins/flow`，正文只装路线部分；在 Claude 侧 `name-only`（自动调用，按 ADR-0004）。
2. agent-config 共用规则：删九段路线与「怎么开始、怎么结束」整节，换成分拣块（十来行）与一句「判为改动落地、或主人敲了段里的 skill，先读 `flow`」；「我在哪」表只留读写边界句。
3. 上线待办里在 Codex、OMP 各开一个「issue N」会话，验证 agent 第一步读 `flow`；读不动就在 AGENTS.md 那一句里写死路径。

### 后果（Consequences）

- 好的：路线改一行只要合并 PR，投影是 junction，不用 sync；路线有 `claude plugin eval` 的对照组守着；要答案和小改动的会话不再背九段。
- 坏的或要承担的：流程分在两个文件，改「三种来往」的判法仍要走 agent-config；第三种会话多一次读 skill 的动作，Codex 与 OMP 的可靠性要靠上线验证。
- 回退：revert 引入本 ADR 的 PR，共用规则的路线段随 agent-config 侧的 revert 回来；`plugins/flow` 从 manifest 摘掉即可。

### 确认（Confirmation）

- 共用规则编译出的 CLAUDE.md／AGENTS.md 里没有段名和门，只有分拣块与读 `flow` 那一句。
- `plugins/flow` 的评测：issue 开场的用例里出现读 `flow` 的动作；自由文本小改动的用例里没有。
- 三个客户端各开一个「issue N」的会话，agent 的第一步都是读 `flow`。
- 落地后回来补实际结果。
