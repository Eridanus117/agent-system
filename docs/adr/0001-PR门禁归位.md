# 三个 Bun 包的 PR 门禁统一到一条矩阵工作流

## 背景与问题（Context and Problem Statement）

2026-09-03 仓库审计时的状态：

| 包 | PR 上谁在跑 typecheck + test | 推 main 时 | 平台 |
|---|---|---|---|
| control-plane | `control-plane-checks.yml`（ubuntu + windows）和 `release-configs.yml` 的 validate-release 作业 | 只有 checks | 3 个作业做同一件事 |
| harness-engine | 无（PR #39 才加了 `harness-engine-checks.yml`） | 无 | 一个真实类型错误因此漏到 main |
| sk | 只有 `release-sk.yml` 的 validate-release 作业 | 不跑 | 只 ubuntu；门禁藏在名叫 Release 的工作流里 |

两条 release 工作流的 release 作业在打 tag 时会自己再跑一遍 install、tsc、test，所以 validate-release 作业的唯一用途就是当 PR 门禁。分支保护（经典模式，strict）要求 5 个必需检查，改工作流名必须同步改分支保护。

请负责人定的一件事：三个 Bun 包的 PR 门禁放在哪条工作流里。

## 决策驱动因素（Decision Drivers）

- 三份几乎相同的 YAML 已经各自漂移（bun 版本、frozen lockfile 不一致），重复本身在制造错误。
- 门禁要在 PR 和推 main 时都跑，且 ubuntu 与 windows 都要覆盖（负责人在 Windows 上开发）。
- 分支保护的必需检查列表不在 git 里，改名要有人同步改设置。

## 考虑过的方案（Considered Options）

| 方案 | 做法 | 适用场景 | 代价 |
|---|---|---|---|
| A 一包一条 checks 工作流 | 给 sk 也加一条；release 工作流去掉 PR 触发 | 包少、想按包看红绿 | 三份重复 YAML，改一处要改三处 |
| B 一条工作区级矩阵工作流 | `packages-checks.yml`：package × os 共 6 个作业，仓库根装一次依赖 | Bun / npm workspace 单仓的常规做法 | 分支保护必需检查从 5 个换成 8 个 |
| C 以 release 工作流的 validate 作业为唯一门禁 | 删两条 checks 工作流 | 想少文件 | 门禁藏在 Release 工作流里，只 ubuntu，harness-engine 仍要特例 |

## 决定结果（Decision Outcome）

选 B。不选 A：重复已在产生错误。不选 C：可读性与平台覆盖都退步。

接入顺序（每步单独可退）：

1. PR #41 加 `packages-checks.yml`，旧工作流不删，6 个作业绿后合并。
2. 分支保护必需检查切为 6 个 `packages (…)` 作业 + `validate` + `conformance`。
3. PR #42 删 `control-plane-checks.yml`、`harness-engine-checks.yml`，两条 release 工作流去掉 `pull_request` 触发与 validate-release 作业。

### 后果（Consequences）

- 好的：门禁一处定义；sk 首次在推 main 时也跑；bun 版本与 lockfile 策略统一。
- 坏的或要承担的：一个包红，整条工作流名显示红，要点进矩阵作业看是哪个包。
- 回退：revert #42 与 #41；分支保护必需检查要手工改回旧的 5 个，这部分 revert 回不去。

### 确认（Confirmation）

- 预期：#42 上 6 个矩阵作业全绿，PR 页面没有一直 expected 的必需检查；合并后推 main 的运行也绿。
- 实际（2026-09-03）：全部成立。中途暴露 control-plane 的 `tests/cli/release-workflow.test.ts` 固化了旧门禁结构（断言 release 工作流必须带 PR 触发），在 #42 内改为断言门禁在 `packages-checks.yml`。
