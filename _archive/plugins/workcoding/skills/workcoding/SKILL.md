# 按任务与风险选规程

本 skill 只路由工程规程，决定哪些规程对当前工程任务必要，不是所有任务的方法选择器，也不拥有所有任务的前置审批。目标是减少理解错误与越权，同时让信息充分的工作直接完成。

## 与外部流程库的边界

Matt 与 Superpowers 的 skill 是可选规程，不是所有任务的前置门。对象、目标行为、授权和验收方式已经明确，且属于局部低风险修复或只读查找时，直接完成本任务；不要仅因为外部 skill 已加载就先进入 `brainstorming`、`using-superpowers`、`using-git-worktrees`、SDD、TDD 或完整 review 流程。只有用户明确要求，或任务本身确实需要对应的规划、隔离、测试、并行或审查能力时，才加载这些外部规程。

## 先判断是否需要路由

按下面顺序处理；命中直接工作分支就退出本 skill，完成用户原任务。

| 当前请求 | 下一步 |
|---|---|
| 用户这次明确要求「先摆路线」「先等我确认」或重开某项决定 | 在指定范围内给路线，等待这次要求的确认；只重开指定事项 |
| 已确认路线、需求或同一项工作的后续步骤，包括「按 workcoding 继续」 | 从上次完成处继续，复用已有决定；提到 skill 名不撤销已有确认，只提出新出现的实质缺口 |
| 首次显式调用本 skill，尚无已确认路线 | 给本次必要路线，等待确认；不扩展到用户未请求的流程 |
| 咨询、只读审查、代码解释、静态查找或查数 | 直接读取有关证据并回答，查不到就说明边界；给优化候选不等于获准实施候选 |
| 权限、资金、数据删除、迁移或生产放量等高风险动作，即使方案明确 | 先核对该具体动作的授权、影响与回退条件；缺的交给用户决定。路线批准不替代动作批准；已有明确批准与充分证据时复用，不重复询问 |
| 对象、目标行为和验收方式明确，局部、可逆且低风险的修复或文字调整 | 在已有授权内实施、验证、交付；不为已有答案重做需求访谈 |
| 需求含糊、存在重要架构取舍、复杂遗留变更或发布决策 | 先补可查证事实，再按下面的缺口表选规程 |
| 用户自己提出尚未判断是否值得建的工具或产品念头 | 交 `clarify` 判断问题，不把它直接转成工程实施 |

**低风险按影响判断，不按行数或文件数判断。** 权限、资金、隐私、数据删除、对外接口、不可逆迁移和生产放量不能因为「只改一行」绕过相应授权。信息不足时先只读核实；不能凭「应该简单」进入实施。

## 事实由 agent 查，取舍由用户定

1. 从当前请求与已有记录提取目标、已有决定、允许动作和验收依据。用户说只读，就只读。
2. 在任务范围内读取代码、配置、文档或现有证据，确认尚缺的是事实还是决定。不要让用户转述本可查到的内容；也不要在没有对象或访问能力时到其他工作区猜。
3. 只把影响行为、范围或风险且不能从现有证据确定的事项交给用户。给出推荐、替代和影响，相关决定合批询问。缺一条决定不阻塞无关的只读调查。

完成判据：已知、未决事项和授权边界能区分；若没有实质未决事项且无需额外授权，就继续工作，不制造「是否允许继续」这一问。

## 按缺口选择最小充分路线

| 当前缺口 | 选择与完成后去向 |
|---|---|
| 外来需求背后的问题、现有做法或价值尚未收口 | `requirement-insight`；已有经确认的问题与判据则复用，不重新访谈 |
| 行为规则或验收例子仍不明确 | `requirement-translation`；已有明确规则与输入／期望输出则直接消费 |
| 既有系统新能力有架构候选、边界或依赖取舍 | `architecture-design`；已经决定的设计不重开 |
| 某个改动决定缺调用影响、耗时或流量证据 | `system-analysis`；普通静态计数直接查，不强套运行时诊断 |
| 复杂遗留代码需要走读，并已选择新旧路径并存的修改策略 | `legacy-change`；普通原地修复不默认套「旧路径零 diff」 |
| 已完成改动需要核对上游、下游、数据或配置接入 | `integration`；没有改变相关边界时不用虚构联调阶段 |
| 明确要求证明旧行为不变，且需要批量输入输出母版 | `evidence-regression`，必须在改代码前采母版；已有回归测试不能冒充真实采集证据 |
| 准备发布、灰度、观测或回滚 | `release-observe`；编写代码或给发布建议本身不授权放量 |

这些是按需组合的入口，不是默认八步流水线。先选当前缺口需要的步骤；后续步骤只在任务确实包含它时列出。没有使用的无关 skill 不逐一报「跳过」，只解释会影响用户预期或风险的取舍。

## 什么时候停下来

- 用户明确要求先给路线时：只给所需路线，等待确认，不提前实施。
- 有实质未决决定、高风险动作尚未获具体授权或缺影响／回退证据时：列出具体缺口、推荐及影响，在该动作前停住。已明确批准同一具体动作且证据齐全时不重复索取批准。
- 没有上述情况时：简短说明做法并继续；不以 skill 被加载过作为必须等待的理由。

需要确认时使用短答，措辞不必机械一致：

```text
任务｜具体对象与要达到的结果
路线｜本次需要的规程、顺序与验证依据
需要你定｜尚未决定的事项；我的建议与主要代价
```

如果用户只要求路线，最后一项就是确认这条路线。若问题是缺源码或环境，说明缺的证据与能继续的部分，不拿路线确认代替访问能力。

## 交棒与结束

- 路线确认后加载选中的下游 skill；步骤、产物与完成判据由下游维护，本文件不复制。
- 交棒时传递具体任务、已确认决定及其来源、允许动作与授权边界、证据位置及其已证明／尚未证明的范围、剩余工作和完成判据；使用该任务已有的记录，不另建一套交接容器。
- 接手时主动读取并消费这些记录，区分已经完成、有证据待核对与仍待执行的工作，从剩余工作继续。已有决定与授权不因换了会话失效，也不换一种问法再问一次；来源缺失或当前状态可能变化时先核实，不把上次的计划、摘要或未经验证的声称当作完成证据。
- 实施中只有目标、风险或授权发生实质变化才重开对应决定；执行卡住先定位原因，不重放整条路线。
- 原有发布、数据、权限与不可逆操作的确认保留。批准路线不等于批准上线，批准一个阶段也不扩大另一个阶段的权限。
- 在已有改动记录中保留被推翻的决定与原因；纯咨询或只读审查直接交付结果，不因加载了本 skill 自动建立文件、Issue 或流程。

## 验证依据

行为用例和实际运行证据见 `evals/`。既要验证复杂任务保留必要确认，也要验证只读、小修、明确授权和已确认续接没有多余等待；单轮回答正确不等于多轮交棒已验证。
