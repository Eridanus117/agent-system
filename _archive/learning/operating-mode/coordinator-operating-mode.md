# 长程多 Agent 协调者的操作模式

> 状态：架构决定输入；不构成实施授权，不改变运行架构、定时器或权威。
>
> 研究日期：2026-08-12。

## 结论先行

推荐目标是**双平面、单调度权、事件优先、周期兜底**：一个确定性或近似无状态的战术操作器持续吸收 Orca 事件，并只在需要判断时拉起一个重新回锚、完成有界工作后退出的战略协调者；5 分钟周期只核对“事件没有告诉我们的负事实”和漏信号，不再续命战略 Session。

迁移顺序应是先取得最关键、也最可逆的收益：把当前长跑协调者改造成“统一入口后的临时协调者”；经影子实验证明重新回锚无遗漏后，再把心跳、收件箱、worktree 观察和去重下沉到战术平面。若战术平面得不偿失，第一阶段本身就是可信的简化目标，不必为了形式上的双层而增加组件。

这份结论针对的是**操作拓扑**，不是模型提示词优化。[关联 #168（映射上下文工程与协调者过载）](https://github.com/Eridanus117/agent-control/pull/168) 已讨论上下文工程；本文只复用其相邻问题，重点回答谁长驻、谁被唤醒、事件和周期如何归一、谁拥有调度权，以及怎样安全换代。

## 问题界定与证据口径

当前设计把三种本应分离的状态绑在同一个长跑 Session 上：

1. **持久控制态**：目标、权威、Issue 合同、决定、所有权、任务图和交付证据；
2. **短暂运行态**：消息、心跳、终端、worktree、某次尝试与超时观察；
3. **推理上下文**：模型当前聊天里的摘要、假设与注意力。

前两者需要可恢复，第三者只能视为可丢弃缓存。当前“CronCreate 每 5 分钟续唤醒 + Orca 把消息持续送入同一 Session”的结构，却用推理上下文承载了逻辑协调者的连续性。这既与“新建 Session 和恢复空闲 Session 都应从持久源重新回锚”的现行入口相冲突，也让两个触发来源各自扮演了调度器。

本文采用四级证据：

- **本次直接验证**：在当前 worktree、GitHub 或 Orca 当前视图中实读、实跑所得；
- **一手来源核验**：系统维护者的正式文档、源码或权威仓库；
- **二手转述**：非维护者对系统的整理；
- **未核验推断**：从已核验事实推出、但尚未在本系统实测的判断。

本文没有用二手转述支撑推荐。凡涉及“在 Orca 中一定可行”或效果幅度的结论，均仍是未核验推断，需用文末实验升级证据。

## 本系统现状：已有底座与真正缺口

### 已有

- GitHub Issue、仓内权威和知识资产已承担持久合同；[协调者换代协议](../../_archive/knowledge/coordinator-succession-protocol.md) 已定义恢复锚点、显式交接和 generation 概念。**证据：本次直接验证。**
- Orca 已有 Run、Task、Dispatch、Delivery 和编排消息；当前 Run 可读到 `consumer_generation: 2`，任务列表为 233 项。它证明运行面已能持久记录大量事实，但“任务很多”本身不等于每条事实都进入模型上下文。**证据：本次直接验证。**
- [当前监控指令](../../work/history/current-monitoring-directive.md) 明确了 5 分钟节奏、合格 Session 数、孤儿 worktree 判断门与“Session 退出后循环消失”。**证据：本次直接验证。**
- `orca automations list --json` 返回空列表；因此当前 5 分钟机制至少不属于 Orca Automation。其具体 CronCreate 载体来自本任务输入和当前指令，本文未做独立实现审计。**证据：本次直接验证 + 任务输入。**

### 缺少

- Orca 事件与 5 分钟周期尚未归一成一个可去重、可回放的协调入口；
- 普通 Run 丢失协调者时的排他接管、租约或 fencing 仍没有实证；已有 generation 不能自动推出“不会双写”；
- 战术处理与战略判断没有权限边界，心跳和消息都能挤占战略 Session；
- 没有明确的 Session 工作预算、退出条件、结构化回锚回执和漏项核对；
- 没有验证过“完全不读旧聊天”的临时协调者能否在一个周期内恢复充分状态。

所以问题不是“有没有持久状态”，而是**逻辑协调者的身份仍和一个物理 Session 绑定，多个触发源又没有经过同一个调度权**。

## 第一性原理

### 1. 身份持久，执行可以短命

逻辑协调者应由“作用域 + 当前权威 + generation/lease + 持久回执”标识，而不是由某个聊天窗口标识。每个物理 Session 可以像一次工作流执行：读取同一个逻辑身份，处理有界输入，提交状态后退出。

Temporal 用事件历史恢复 Workflow；worker 是瞬时进程。其 Continue-As-New 会保留逻辑 Workflow ID，同时用新执行和干净历史继续；Child Workflow 用于把大生命周期分片。这是一种很贴近本问题的持久执行类比，但并不证明 Orca 已具备同等语义。**证据：一手来源核验；迁移到 Orca 的结论是未核验推断。** [Temporal 文档](https://docs.temporal.io/)、[Temporal 架构](https://github.com/temporalio/temporal/blob/main/docs/architecture/README.md)、[Temporal 模式](https://go.temporal.io/platform-hub/patterns)

### 2. 触发源可以多个，调度权只能有一个

“事件”和“定时 tick”是输入，不应各自决定动作。二者先归一成同一作用域的 reconcile 请求，再由一个活动协调者串行计算、去重和提交。高可用副本也不等于多个活动调度者：Kubernetes 协调式 leader election 允许多副本存在，却用 Lease 和乐观并发控制选出一个活动 leader。**证据：一手来源核验。** [Kubernetes 协调式 leader election](https://kubernetes.io/docs/concepts/cluster-administration/coordinated-leader-election/)

这条原则不要求只有一种唤醒方式，而要求所有唤醒都经过同一消费序列、同一 ownership/fence 和幂等回执。当前双入口的核心问题不是数量“二”，而是两者都能延长并驱动同一聊天执行，且没有显式归一与消费语义。

### 3. 有事件时按事件，没有事件时只核对负事实

消息到达、`worker_done`、owner 回复、Delivery 到达都是正事件，事件驱动比盲轮询更低延迟、更少重复读取。Kubernetes API 的 list/watch 正是用初始快照加增量事件维护视图，并以 `resourceVersion` 处理续接；其控制器仍保留周期性 resync 作为安全网。**证据：一手来源核验。** [Kubernetes API list/watch](https://kubernetes.io/docs/reference/using-api/api-concepts/)、[kube-controller-manager resync 参数](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-controller-manager/)

但“5 分钟内没有新增合格 Session”“某个尝试已静默超时”“可能存在漏事件”等是负事实，单靠没有到来的事件无法判断。因此正确取舍不是纯事件或纯轮询，而是**事件优先、周期兜底**：周期只做短小、幂等的全量核对，不能借机让战略 Session 永生。

### 4. 战术活动和战略判断需要权限分层

OpenAI Agents SDK 区分由 LLM 自主编排和由代码编排；代码编排更确定、可预测，manager-as-tools 则让管理者保留控制。它没有规定本系统的具体架构，但支持把可机械化操作放在确定性层，把需要语义判断的动作留给管理者。**证据：一手来源核验；本系统分层是未核验推断。** [OpenAI Agents SDK 多 Agent 编排](https://openai.github.io/openai-agents-python/multi_agent/)

战术平面可以做：收取和去重消息、记录 observedAt、水位与尝试状态、核对心跳、读取 worktree 证据、产生结构化升级包。它不能改产品决定、扩授权、判断验收、跨所有权派发或自创持久真相。战略协调者只在出现决定门、授权变化、假设翻转、新波次或里程碑时被唤醒。

### 5. Compaction 是退路，不是生命周期

Claude Code 会在上下文接近上限时自动压缩，清理旧工具输出并摘要对话；官方同时警告早期详细指令可能在压缩中丢失，并建议把持久规则放入 `CLAUDE.md`。其 subagent 使用独立上下文，完成后只回传摘要。**证据：一手来源核验。** [Claude Code 工作原理](https://code.claude.com/docs/en/how-claude-code-works)、[Claude Code 上下文窗口](https://code.claude.com/docs/en/context-window)、[Claude Code subagent](https://code.claude.com/docs/en/sub-agents)

这说明主动压缩和子上下文隔离都有价值，却不能替代“持久源回锚 + 有界执行 + 退出”。压缩保住的是一段聊天的近似连续性；我们需要的是逻辑任务的可验证连续性。

### 6. 大跨度应按权威作用域分片

LangGraph 在每一步保存 checkpoint，以 `thread_id` 恢复；interrupt 要求恢复时使用同一线程标识，副作用必须幂等。AutoGen team 也有停止条件和 save/load 状态，并警告把同一 team 用于不相关任务前应 reset。**证据：一手来源核验。** [LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)、[LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)、[AutoGen team](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)、[AutoGen 状态](https://microsoft.github.io/autogen/dev/user-guide/agentchat-user-guide/tutorial/state.html)

对本系统的启示是：同一 Issue 子树内可以维持一个逻辑协调线程；跨子树只交换里程碑、依赖和决定，不把所有 worker 细节复制到父级。是否需要分片由跨度、依赖和回锚成本决定，不由 Session 数量决定。**证据：未核验推断。**

## 候选目标模式

### 模式 A：单层临时协调者 + 统一触发队列

Orca 事件和周期 tick 先变成同一种带作用域、水位和原因的 reconcile 请求。一个 fresh Session 取得该作用域的排他消费权，按固定锚点恢复，完成一个决定、一个波次或一次核对，写回回执后退出。

| 维度 | 映射与评价 |
|---|---|
| 已有 | GitHub/权威持久态、Orca Run/Task/Dispatch/Delivery、恢复锚点、generation 概念 |
| 缺少 | 统一队列或等价消费入口、普通 Run fencing、fresh Session 拉起、结构化回执、退出预算 |
| 迁移成本 | 低到中；主要改变生命周期和入口，不必先造完整战术组件 |
| 风险 | 回锚慢或漏项；没有 fencing 时重复动作；频繁启动增加延迟和模型成本 |
| 可逆性 | 高；影子模式不写入，回退只需恢复旧消费方式 |
| 过载净收益 | 高；每次战略上下文有界，不再继承全部聊天 |
| 委托净收益 | 中；仍由战略协调者读取较多运行细节 |
| 可靠性净收益 | 中到高；取决于队列、幂等与 fencing 是否真实成立 |

它是最小可信目标，也是推荐迁移的第一阶段。

### 模式 B：双平面战术操作器 + 临时战略协调者

战术操作器成为唯一持续消费者：处理消息、心跳、状态投影、worktree 证据和 5 分钟安全核对；只有结构化升级条件命中时，才拉起 fresh 战略协调者。战略层重新读取持久锚点，做需要判断的有限工作，写回决定或派发事实后退出。战术层只保存可重建投影和消费回执，不建第二套权威。

| 维度 | 映射与评价 |
|---|---|
| 已有 | Orca 消息和任务状态、5 分钟监控合同、战略/战术语义边界的相邻研究 |
| 缺少 | 战术消费者、升级 schema、去重水位、fresh 战略拉起、权限负面清单、fail-open 路径 |
| 迁移成本 | 中；需要一个可靠而克制的战术组件及其验证 |
| 风险 | 误判导致漏升级或过度升级；战术投影若越权会形成第二真相；组件维护成本 |
| 可逆性 | 中到高；先 shadow，且战略层可直接接管全部事件 |
| 过载净收益 | 最高；高频低价值事实不进入战略上下文 |
| 委托净收益 | 高；战略层接收的是结构化差异和决定门，而非原始噪声 |
| 可靠性净收益 | 高；常驻的是确定性消费和核对，不是易漂移的推理对话 |

这是推荐终态。推荐它的前提是战术层保持无产品决定权、可重建，并且所有动作仍受单一 scope fence 约束。

### 模式 C：联邦分片临时协调者

每个 Issue 子树拥有自己的逻辑协调线程和临时执行；父级只消费子树的里程碑、依赖、风险和决定请求。每个分片内部仍遵守单调度权，跨分片动作必须通过明确合同和所有权路由。

| 维度 | 映射与评价 |
|---|---|
| 已有 | 父/子 Issue 权威结构、Run/Task/Dispatch、各 Session 按合同取得所有权的规则 |
| 缺少 | 分片级 fencing、跨分片依赖协议、父级差异摘要、全局不变量检查 |
| 迁移成本 | 中到高；涉及拓扑和跨域一致性，不适合作为第一步 |
| 风险 | 依赖遗漏、重复派发、父级失去全局约束、跨分片死锁 |
| 可逆性 | 中；可先只把一个独立子树作为试点 |
| 过载净收益 | 高；规模随子树分摊 |
| 委托净收益 | 高；所有权边界更贴近合同 |
| 可靠性净收益 | 中到高；局部故障隔离更好，全局一致性更难 |

它是规模化扩展，不是当前首选。若未来主要瓶颈从“一个 Session 过载”变成“多个独立子树同时活跃”，它才可能翻转为推荐。

### 对照：长跑 Session + 主动 compaction

仅给现状增加上下文预算、摘要和 `/compact`，可短期减轻 token 压力，却仍让两个触发源续命同一个物理执行，也没有解决单调度权、排他接管和重新回锚的可验收性。它可作为迁移期间的止痛措施，不是可信终态。

## 推荐与迁移建议

### 推荐

采用**模式 B，经过模式 A 迁移**：

1. 先把 Orca 事件与 5 分钟 tick 归一为一个 reconcile 入口；以 fresh Session 完成“回锚—有界处理—持久回执—退出”。
2. 先影子运行，不让新路径产生外部动作；用同时间截面的结果与当前协调者核对。
3. 验证无遗漏、无重复、可在周期内完成后，才让临时协调者承担一个明确、可逆且已授权的动作。
4. 再把高频机械工作下沉到战术平面；战略层只接收差异、决定门和需授权事项。
5. 最后按实际跨度决定是否启用模式 C；不要预先建设联邦拓扑。

对 5 分钟机制的目标语义是“安全 reconcile”：核对合格 Session 数、静默尝试、孤儿候选和漏事件。它既不是第二调度器，也不能续命战略 Session。对 Orca 事件的目标语义是“低延迟触发”；它不能绕过同一 scope 的消费权与幂等提交。

### 会翻转推荐的未知

| 未知 | 若证据为真，推荐如何变化 |
|---|---|
| 当前没有任何外部机制能可靠拉起 fresh Session | 暂保留现有长跑执行作为过渡载体，但仍先统一触发并限制工作预算；不能把模式 B 当成可实施 |
| Orca 事件对所需类别不可重放、可能丢失或没有稳定水位 | 周期 reconcile 暂做主路径，事件仅降延迟；先补证据再转事件优先 |
| 普通 Run 无法提供单活动协调者的 fencing | 不进行自动换代；只允许显式、计划内交接，直到排他语义被验证 |
| fresh Session 回锚平均无法在下一次 5 分钟 tick 前完成，或会漏掉活动 Dispatch、Delivery、owner 动作 | 模式 A 暂不合格；优先建设常驻战术操作器，战略仍临时 |
| 战术升级的漏报代价或维护成本大于减少的战略负载 | 以模式 A 为终态，不引入模式 B |
| 同时活跃且相互独立的 Issue 子树成为主瓶颈 | 模式 C 升为优先，但仍先验证每个分片的单调度权 |

## 最小验证实验：临时协调者回锚循环

这是一项待批准的验证设计，不是本文已执行的改动。

### 实验设置

- 选择同一 Issue/Run 的 3 个连续 5 分钟周期，或一个自然工作波次；
- 每轮启动一个不读旧聊天的 fresh 协调者；旧协调者只作观察对照，仍是唯一行动者；
- 输入固定为：当前监控指令、活动 Issue 合同及其链接权威、Run/Task/Dispatch/Delivery 当前视图、所有权范围和来源 observedAt；
- fresh 协调者只产生一份结构化 reconcile 回执：各来源水位、当前 owner、活动尝试、未消费事件、候选动作、需决定事项、无动作理由和所有权歧义；
- 在相同时间截面比较 fresh 回执与旧协调者判断，影子路径不派发、不清理、不改权威。

### 通过条件

- 每轮在下一次 tick 前完成；
- 活动 Dispatch、待处理 Delivery、负责人动作和所有权冲突零遗漏；
- 没有重复派发、重复释放或重复清理建议；
- 无需读取旧聊天即可解释每一项建议的来源；
- 来源水位和不确定项显式，不把未知默认为无动作；
- 战略输入只包含锚点与相关差异，原始心跳和重复消息不进入最终判断上下文。

若影子阶段通过，再申请让 fresh 协调者执行一个已授权、可逆的动作，例如路由一个只读研究任务或生成一个决定请求。任何双写、漏消息、无法证明当前 owner、无法在周期内完成，或必须依赖旧聊天的情况，都立即停止实验并保留现状。

这项实验最多把证据升级到“当前场景交付样本”；它不能单独证明长期稳定性，也不能验收整个目标模式。

## Authority 候选

以下内容适合在负责人作出架构决定后评估是否收敛进 authority；它们当前都只是候选，本文不修改 authority：

1. **A1｜Session 可丢弃**：逻辑协调者的连续性来自持久权威、运行事实和 generation/lease；推理 Session 是有预算、可退出的执行缓存。
2. **A2｜单调度权**：同一 Issue 子树、Run 或共享资源在任一时刻只有一个活动 reconcile 权；事件、周期和人工唤醒只是输入，不是独立调度器。
3. **A3｜事件优先、周期兜底**：正事件即时触发；周期只核对负事实、超时和漏事件，不能续命战略 Session。
4. **A4｜战术无决定权**：战术操作器可消费、投影、去重和升级，但不能扩授权、改变产品决定、跨所有权派发或成为第二真相。
5. **A5｜有界战略执行**：战略协调者每次只完成一个决定、一个波次或一个里程碑；达到预算或边界即写回结构化回执并退出。
6. **A6｜按权威作用域分片**：需要扩容时优先按 Issue 子树分片，并显式维护跨分片依赖；不能仅按终端或 Provider 数量拆分。

其中 A1、A2、A3 是模式 A 和模式 B 的共同基础；A4 是采用模式 B 的新增边界；A5、A6 是上下文和规模的护栏。最先需要负责人决定的不是“要不要造战术组件”，而是是否接受 A1—A3 作为目标操作原则。

## 决定建议

建议负责人先决定：**接受 A1—A3，并批准仅影子的临时协调者回锚实验；暂不决定战术组件实现。** 影子证据能低成本回答最关键的翻转未知——fresh Session 能否在 5 分钟窗口内无遗漏地恢复——随后再在模式 A 与模式 B 之间作实施决定，避免把未经验证的“正确架构”直接变成新的长期依赖。
